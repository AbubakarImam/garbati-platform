# T-051: Public-facing explainer site, hosted on GitHub Pages, auto-synced to the real docs

Target repo: `garbati-platform`. Branch: `feature/public-docs-site`.

## Context

GARBATI has no single entry point for a researcher, recruiter, or potential contributor to understand
what this platform is and how it fits together before diving into six separate repos. `README.md`,
`ARCHITECTURE.md`, `DEPLOYMENT-RUNBOOK.md` and `research/*.md` are all real and thorough, but they are
plain markdown files inside a cloned repo — nothing hosted, nothing designed, nothing that reads as a
guided introduction. This was never flagged as a gap by T-037's own OSS-readiness benchmark (which
checked for `LICENSE`/`CONTRIBUTING`/`SECURITY.md`-type files, not a documentation site) — it's a new,
distinct idea from the owner, not a previously-deferred item.

**Owner's explicit requirements**: a genuinely designed, "marketing style" site (not a generic docs-theme
dump), that gets a real, permanent, public URL, and **stays in sync automatically whenever the source
docs change** — no manual rebuild step, no content that can silently drift from the real `ARCHITECTURE.md`/
`DEPLOYMENT-RUNBOOK.md`/`research/` files.

## Technical approach: GitHub Pages' native Jekyll build, not a custom pipeline

GitHub Pages rebuilds a Jekyll site automatically on every push to the configured branch/folder — no
GitHub Actions workflow needs to be authored for this (Pages' own build service handles it). This is what
satisfies "stays in sync automatically" with the least moving parts, and it's free.

- Build from a `/docs` folder on `main` (the common GitHub Pages convention — do not use a separate
  `gh-pages` branch, which would need its own sync mechanism).
- `docs/_config.yml` — standard Jekyll config, `markdown: kramdown` (GitHub Pages' default processor).
- **The two reference pages that mirror existing docs (architecture, replicate) must pull the ACTUAL
  current file content at build time via Jekyll's `{% include_relative %}` Liquid tag, pointing at the
  real files one directory up** (`{% include_relative ../ARCHITECTURE.md %}`, `{% include_relative
  ../DEPLOYMENT-RUNBOOK.md %}`). Do **not** hand-copy their content into `docs/` — a copy is exactly the
  drift risk the owner explicitly asked to avoid. Confirm this actually works (Jekyll includes outside the
  site source need `include_relative`, not `include`, and GitHub Pages must permit reading one directory
  above `docs/` — verify this builds correctly before considering the task done, not just assumed).
- The research index page should list `research/*.md` by **iterating the directory at build time**
  (Jekyll's `site.static_files` or a custom data file generated by a tiny pre-build step — check what's
  actually feasible without a custom Action first; if Jekyll alone can't enumerate an external directory's
  files, the fallback is a GitHub Actions workflow, triggered on push to `research/**`, that regenerates a
  single `docs/_data/research_index.yml` file the page reads — only resort to this if the simpler native
  approach genuinely doesn't work, and explain which one was used and why in the PR).
- **Enabling GitHub Pages itself** (Settings → Pages → source: `main` branch, `/docs` folder) is a repo
  setting change, not a file in this PR — note in the PR description that this still needs to be switched
  on by the owner (or via `gh api repos/AbubakarImam/garbati-platform/pages` if that's available to you;
  if it requires owner-level repo administration beyond what's available, say so plainly and leave it as
  the one explicit manual step rather than silently skipping it).

## Design plan — follow this, don't default to a generic docs theme

**Concept**: a ledger register, not a typical SaaS landing page. The subject is a double-entry core
ledger — lean into that directly (hairline rules between sections like ledger rows, tabular numerals for
every number on the page, real structure) rather than a generic hero-with-gradient template.

**Color tokens** (define all of these in `:root`, redefine only under the dark-mode guards — see below):
- `--ground: #F4F6F3` (pale, cool sage-white — not cream) — page background, light mode
- `--ink: #10262B` (near-black with a teal cast) — primary text, light mode
- `--teal: #1E5159` (deep teal) — the dominant brand color: headers, links, section rules
- `--brass: #B9862E` (warm brass/gold) — the **one** accent color, spent sparingly (a single stat
  highlight, the one CTA button, hover states) — never used as a second dominant color
- `--line: #C9D3CC` (muted sage-grey) — hairline rules between sections, table borders
- Dark mode (`prefers-color-scheme: dark`, following this project's own artifact dark-mode convention of
  swapping roles consistently, not just inverting): `--ground: #0E1A1C`, `--ink: #E9EDE9`, `--teal:
  #5FA3AC`, `--brass: #D9A94B`, `--line: #27393C`.

**Typography**: three roles, all from Google Fonts (`<link rel="stylesheet" href="https://fonts.googleapis.com/css2?...">`,
with a real fallback stack each).
- Display (`h1`/`h2`, section labels): **Fraunces** — a characterful soft-serif, not a generic sans. Use a
  real weight range (400/600/900), not just one weight.
- Body: **Work Sans** — clean, highly legible, not `Inter` (deliberately avoided — see the "avoid
  AI-generated design" guidance already followed elsewhere in this project's own artifacts).
- Numbers, code, every stat/count on the page: **IBM Plex Mono**, with `font-variant-numeric:
  tabular-nums` wherever digits sit in a column — this is a banking ledger site; numbers aligning matters.

**Layout, concretely**:
- **Hero**: states the thesis plainly in one or two lines — what GARBATI is (open-source core banking for
  Sharia-compliant microfinance) and what makes it concrete (real services, real ledger, real research —
  not a mockup). No large background gradient, no stock-photo hero image. Below it, a tabular-numeral stat
  strip pulled from real, current facts — e.g. services shipped, decisions logged, tasks closed — sourced
  by actually reading `TASKS.md`'s real current counts at the time of writing (count the actual `| T-` and
  `| D-` rows, don't invent round numbers), stated as "as of <date>" so it's honest about not being live.
- **Architecture-at-a-glance**: a real inline SVG diagram of the actual 6 live services and how they call
  each other, matching `ARCHITECTURE.md`'s own service map exactly (LedgerApi, IdentityApi,
  OrchestratorApi, StaffIdentityApi, OpsApi, ProductApi, plus the ops-console frontend) — not a generic
  "microservices" stock diagram. Follow this project's own diagramming discipline: label every arrow with
  what actually flows (a call, a scope check), use `currentColor` so it works in both themes, size by a
  real `viewBox`. This diagram's data must match `ARCHITECTURE.md`'s service map at the time it's built —
  if that map changes later this diagram will need a manual update (acceptable; say so directly in the PR
  rather than pretending every diagram is auto-synced, since only the text-pull pages are).
- **"How to replicate it yourself"** section on the home page: a short, honest teaser (the real
  one-command `docker-compose up` workflow from T-038, with the actual command), linking to the full
  `/replicate/` page for the complete runbook content.
- **Section rule lines**: a thin `--line`-colored horizontal rule between major sections, with a small
  uppercase label in `--teal` sitting on the rule (like a ledger row header) — this is the one recurring
  structural device; don't invent numbered markers (01/02/03) unless a section is genuinely a sequence.
- Standard responsiveness/dark-mode/gutter rules apply (phone-width tested, side gutter ≥16px, no
  horizontal scroll except wide tables/diagrams in their own `overflow-x:auto` container).

**Pages**:
1. `docs/index.md` (home) — hand-written marketing copy per the hero/architecture/replicate-teaser shape
   above. This is the one page that is genuinely hand-authored, not pulled from another file.
2. `docs/architecture.md` — `{% include_relative ../ARCHITECTURE.md %}` inside the shared layout.
3. `docs/replicate.md` — the real quickstart + `{% include_relative ../DEPLOYMENT-RUNBOOK.md %}`.
4. `docs/research.md` — an index of every file in `research/`, generated per the technical approach above.
5. `docs/_layouts/default.html` — the shared header/nav/footer shell carrying the design above. Nav links:
   Home, Architecture, Replicate It, Research, and a direct GitHub link (to `garbati-platform` itself — no
   reason to hide where the real source lives).

## Explicitly out of scope

- Do not rebuild or restyle `garbati-ops-console` — unrelated, different audience, not touched by this
  task.
- Do not render `TASKS.md` or `LEARNING_LOG.md` as site pages — they're enormous working logs, not
  introductory reading. Link out to them on GitHub directly from wherever feels natural (e.g. a "want the
  full decision history?" line), rather than reproducing them.
- Do not write a `CONTRIBUTING.md` or change D-22's "agent/coordinator-driven for now" posture — this site
  explains the project to readers, it does not change who can contribute code.
- Do not invent a different architecture than what `ARCHITECTURE.md` actually documents — if something on
  the real service map is unclear, read the actual file again rather than guessing.
