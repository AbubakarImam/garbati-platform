# T-023: Research — gRPC vs HTTP/REST for GARBATI's inter-service calls

Output file: `research/grpc-vs-rest-inter-service.md`. This is research only — no code, no design decision. The owner noticed every current inter-service call (OrchestratorApi → IdentityApi, OrchestratorApi → LedgerApi) is plain HTTP/JSON and asked whether gRPC would reduce latency, plus wants an explanation they can actually follow (they are a C#/.NET learner, not yet experienced with gRPC or distributed-systems performance work).

## Context

Today: `Garbati.OrchestratorApi` calls `LedgerApi` and `Garbati.IdentityApi` over plain HTTP with JSON bodies and an `X-Api-Key` header (see `Garbati.OrchestratorApi/docs/DESIGN.md` and its actual `Clients/Implementations/*.cs` source for the real shape). All three services are ASP.NET Core 8 on .NET 8. Read `garbati-platform/ARCHITECTURE.md` Section 5 (shared conventions) for the platform-wide API rules this would need to coexist with or replace (versioning, idempotency, error-shape, correlation IDs, service authentication).

Important framing: switching any existing inter-service call to gRPC would be an **API contract change** and would **add a new dependency** (the gRPC libraries) — both explicitly named as human-only gates in `garbati-platform/AGENTS.md`. This research informs a decision the owner has not yet made, not a recommendation to implement anything.

## Questions to answer

1. **What is gRPC, in plain terms, compared to what GARBATI does today?** Explain Protocol Buffers (`.proto` files), HTTP/2, and binary serialization at a level a C#/.NET learner can follow — use a concrete analogy if one helps. What specifically makes it faster than JSON-over-HTTP/1.1, and by roughly how much in real published benchmarks (cite sources, don't just assert a number) — for a payload shape similar to GARBATI's (small-to-medium JSON objects: account numbers, amounts, customer ids).
2. **Does gRPC make practical sense for GARBATI's actual calls today?** OrchestratorApi's calls to IdentityApi/LedgerApi are synchronous, small-payload, low-fan-out (a handful of calls per customer operation, not thousands per second yet). Is gRPC's latency advantage actually meaningful at this scale, or is it a solution to a scaling problem GARBATI doesn't have yet? Look for real-world guidance on when gRPC's benefits start to matter (request volume, payload size, fan-out degree) versus when the switching cost isn't worth it.
3. **What would adopting it concretely involve in ASP.NET Core 8?** The `Grpc.AspNetCore` package, defining `.proto` contract files (would these live in `garbati-platform/contracts/` alongside or instead of whatever OpenAPI-equivalent exists today?), code generation, and whether gRPC and the existing REST/Swagger endpoints can coexist on the same service (so Swagger-based demo access for recruiters, which the whole platform's current demo strategy depends on, isn't lost).
4. **What do real fintech/banking microservice systems actually do here?** Is gRPC common for internal service-to-service calls in payments/banking systems specifically (as opposed to generic microservices advice)? Any cautionary notes specific to money-moving systems (e.g., does gRPC's binary format make request/response logging and audit trails harder to produce in human-readable form, which matters given GARBATI's audit requirements)?
5. **What are the real downsides and lighter alternatives?** Load balancer/proxy compatibility (does Azure App Service, which LedgerApi/IdentityApi already deploy to, support gRPC cleanly?), debuggability compared to curling a JSON endpoint, browser-based tooling limits. Also cover lighter latency improvements that don't require a protocol change at all (HTTP connection pooling/keep-alive via `IHttpClientFactory`, which GARBATI may already get for free from ASP.NET Core defaults; response compression; `HttpClient` reuse) — are these likely to close most of the latency gap without a contract-breaking migration?

## Format

Write `research/grpc-vs-rest-inter-service.md` with: a plain-language summary up top (the owner is a C#/.NET learner — define every term, including ones that seem obvious, like "serialization" or "binary protocol," on first use), sourced answers to the five questions with real benchmark citations where you make a speed claim, then a **"Recommended path for GARBATI, explained simply"** section — a clearly-labeled recommendation (not a decision) walking through, in plain steps, what adopting gRPC would actually look like for one single call (e.g. OrchestratorApi → LedgerApi's transfer call) if the owner wanted to try it, specifically so a learner could follow along and understand the mechanics, even if the recommendation is "don't do this yet." End with a "What this does not settle" section.
