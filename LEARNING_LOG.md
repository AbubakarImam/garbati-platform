### 2026-10-19: Reversal execution + an approvals queue to browse (Garbati.OrchestratorApi PR #4, Garbati.IdentityApi PR #5; T-030, T-031, D-14/D-15)
**In plain words:** Designing the ops console's backend (OpsApi, T-028) surfaced two real missing pieces on already-shipped services, not invented work: IdentityApi could *authorize* a reversal (built back in T-020) but nothing could actually *execute* one — OrchestratorApi had no reversal endpoint at all. And IdentityApi could only fetch one pending joint-account approval by its id, never list them — so an "approvals queue" screen would have had nothing to browse. T-030 built the missing execution endpoint (ask IdentityApi, execute on LedgerApi, report back what really happened); T-031 built the missing list endpoint. Both are additive — nothing existing changed behavior.

T-030 is the one that mattered most, because QA's first review of it found a real bug, not a style nit: the code only handled one of LedgerApi's four possible responses to a reversal attempt (a clean business-rule failure). Every other outcome — the transaction not found, a sign that it was *already* reversed by an earlier attempt, or a genuine server error — fell through as an unhandled crash, which meant IdentityApi's own record of "did this reversal happen or not" was simply never updated. Money could be perfectly fine at the ledger level while the system's own paperwork about it silently went missing forever. The fix treats each of LedgerApi's four possible answers on its own merits — including the subtle one: if LedgerApi says "this was already reversed," that means the money already came back on an earlier, lost-response attempt, so the right thing to tell IdentityApi is "yes, this succeeded," not "this failed" and not nothing at all.

**Five interview questions:**
1. Q: Why does LedgerApi saying "409, already reversed" get reported to IdentityApi as success, not failure?
   A: A 409 there means a reversal row for that exact original transaction already exists — i.e., the money already moved back on some earlier attempt whose response never made it back to the caller (a lost network response, say). The customer's money is fine; what's missing is just the confirmation. Reporting "failed" or doing nothing would leave IdentityApi believing something untrue or nothing at all, when the true answer is simply "yes, already done."
2. Q: QA said the first version of this code had a real bug, not just a nitpick. What made it a real bug and not just messy error handling?
   A: Because the consequence wasn't cosmetic — it meant IdentityApi's record of a reversal's outcome could be permanently and silently lost, with no process anywhere in the system designed to notice or fix that gap. A messy-but-harmless style issue doesn't lose data forever; this did.
3. Q: How did QA actually prove the fix worked, rather than just reading the code and agreeing it looked right?
   A: By breaking it on purpose — deliberately changing the fixed code back to the old, wrong behavior, rerunning the tests, and confirming they failed with exactly the expected mismatch. Only after seeing the test catch the deliberately-reintroduced bug, and then seeing it pass again once the fix was restored, did QA treat the fix as actually proven rather than merely plausible.
4. Q: This PR found that IdentityApi's reversal-request endpoint has no protection against a caller accidentally asking for the same reversal twice. Why wasn't that fixed here too?
   A: Because it's a separate, pre-existing issue on a different service's already-shipped code, not something this task touched or introduced — fixing it here would have meant quietly expanding this task's job into someone else's. It's written down as its own flagged item (D-16) so it doesn't get forgotten, rather than either silently fixed (scope creep) or silently ignored.
5. Q: Why wasn't the IdentityApi "list pending requests" change (T-031) treated as a bigger deal, the way the reversal fix was?
   A: Because it genuinely is simpler and lower-risk by its nature — it only reads data and was carefully checked to prove it never shows a single-holder request that doesn't actually need anyone's approval. QA still found and the coordinator still fixed one real rough edge (a request already past its deadline could keep showing as "still waiting" until something else happened to touch it) — smaller stakes don't mean no scrutiny, just a different scale of consequence if something had been missed.

**One thing that nearly went wrong:** The very first builder assigned to the IdentityApi-vs-OrchestratorApi responsibility split (who asks for permission, who actually carries out the action) had it backwards in an early draft of the ops console's own design — the piece meant to just track staff approvals was going to also ask IdentityApi for the authorization grant itself, while a separate piece was going to carry out the result. That split didn't match how every other part of this platform already works, where the same component that asks "am I allowed" is also the one that follows through — asking and doing kept together, not split across two different services that then have to stay in sync with each other. It was caught and corrected before any code was written against it, simply by checking the new design against the pattern already proven to work elsewhere, rather than letting a plausible-sounding design go untested against precedent.

### 2026-10-18/19: Real Azure deployment + two bugs only live testing could find (Garbati.OrchestratorApi PR #2/#3, Garbati.IdentityApi deploy wiring; T-024, T-025)
**In plain words:** Until now, IdentityApi and OrchestratorApi existed only as code that passed tests on a laptop — they had never run against real Azure infrastructure, talking to each other and to the real deployed LedgerApi over the real internet. This round wired both of them up to real Azure App Services (sharing LedgerApi's existing App Service Plan and Postgres server to avoid paying for brand-new infrastructure), then proved it by actually running the full demo end to end: open a customer account, fund it, transfer money to a second account — for real, not against mocks. The first two attempts at the transfer step failed, and both failures were real bugs that every unit test in the repo had missed, because tests only ever talk to fake stand-ins for the other two services. Live testing against the real thing caught what mocks structurally cannot.
**Five interview questions:**
1. Q: The unit tests for the transfer feature passed the whole time. How did a bug that breaks every single real transfer get through?
   A: The tests mock `IIdentityApiClient` directly — they hand it a request and assert the mock was called, but never check *what value* was actually put in the `Operation` field, and the fake never validates it the way the real IdentityApi does. OrchestratorApi was sending the literal string `"Transfer"`, which doesn't exist in IdentityApi's actual vocabulary (`View`/`Debit`/`Credit`) — so every live call got rejected with a 400, which OrchestratorApi's own error handling then quietly turned into a generic, undiagnosable 500. A transfer is really asking "may this person debit this account," so the fix was to send `"Debit"` — the word IdentityApi's contract already has for exactly that question.
2. Q: After that was fixed, the second live transfer attempt *still* failed — with a completely different, correctly-formed error this time. What was that, and why wasn't it a sign the first fix was wrong?
   A: It was IdentityApi correctly saying "no" for a real reason: `422 OperationNotEligibleForKycTier`. That's the system working — a genuine authorization denial, not a crash. The cause turned out to be a second, independent bug: OrchestratorApi's demo-account stub always marks new customers as KYC tier "Tier1", but IdentityApi's own seed data only allows a Tier1 customer to *View* an account, never move money in or out of it — only Tier2 and above can. Two services each made a reasonable, independently-documented placeholder choice that didn't fit together.
3. Q: Why was the fix "change the demo stub to Tier2" and not "change IdentityApi's Tier1 policy to allow transfers"?
   A: Because Tier1-can't-move-money is the *correct* real-world rule (an unverified identity shouldn't be able to move funds) — that's not the bug. The bug was entirely on OrchestratorApi's side: its own demo stub picked a tier that didn't match what it needed to demonstrate. Fixing it meant picking a different already-existing placeholder value in OrchestratorApi's own code, not touching IdentityApi's policy at all.
4. Q: Both fixes added a "regression test." What makes a regression test here actually prove anything, rather than just existing for show?
   A: In both cases, QA didn't just read the test and assume it worked — QA mechanically reverted each fix back to the broken value, reran the suite, and watched the new test fail with exactly the expected mismatch, then restored the fix and watched the suite go green again. That's proof the test would have caught the original bug, not just a plausible-looking assertion.
5. Q: The first builder agent assigned to fix the second bug (T-025) stalled partway through and never finished. What happened to that work?
   A: Its half-finished diff was still sitting in the repo, unstaged — and it was already the right fix, just missing the test and the commit/PR. Rather than throwing it away and starting over, the coordinator read the existing diff, verified it was correct and complete, wrote and ran the missing regression test, and finished the commit/PR itself. The work a stalled agent leaves behind is still worth checking before discarding it.
**One thing that nearly went wrong:** Both bugs were invisible to every form of testing in this platform except the one that was actually run: a real call against real deployed services. If the first manual end-to-end verification hadn't been done — if "deploy it" had been treated as done once CI's `test`/`docker`/`deploy` jobs went green — both bugs would have shipped silently, and the very first real customer transfer attempt (whenever that happened) would have failed in production with no warning. The lesson carried forward: for a system built from several services that each mock the others in their own tests, passing CI in every repo is not the same as the whole system actually working together.

### 2026-10-18: OrchestratorApi foundation — account opening and transfer (Garbati.OrchestratorApi, PR #1)
**In plain words:** Until now, every service in GARBATI existed on its own — LedgerApi moves money, IdentityApi decides who's allowed to move it, but nothing actually called them both in the right order. This is that missing piece, for its first and simplest two jobs: opening a new customer's account (four steps across two services, resumable if it fails partway through) and moving money between two accounts (ask IdentityApi "is this allowed?", and only if yes, ask LedgerApi to actually do it). It deliberately skips fees and reversals — those need pieces that don't exist yet — and it still trusts whoever calls it about which customer they are, since there's no real login system in front of it yet. Both of those gaps are written down, not hidden.

**Five interview questions:**
1. Q: If this service crashes right after creating someone's ledger account but before attaching their mandate, and you retry the whole operation, how do you know a second ledger account doesn't get created?
   A: Every step sends the same unique key to the other service every time it's attempted, derived from the operation's own ID. LedgerApi's own rule is that repeating the same key just hands back what it already created instead of making something new — so retrying is always safe, even from the very first step.
2. Q: Why does a denied transfer never even attempt to call LedgerApi?
   A: Because the two steps happen strictly in order and the code simply stops the moment IdentityApi says no — there's no code path that reaches LedgerApi without first getting a yes. A test specifically counts how many times each downstream service got called to prove this, rather than just trusting the code looks right.
3. Q: This service was tested against fake, stand-in versions of IdentityApi and LedgerApi rather than the real ones running live. What's the actual risk in that?
   A: The fakes were built directly from copies of the real services' actual response shapes, so a mismatch in an obvious field would likely have been caught. What it can't catch is the real services changing their behavior later without this service's fakes being updated to match — that gap was stated plainly rather than hidden, and the honest fix is an occasional real end-to-end check, not a redesign.
4. Q: Why doesn't this service check IdentityApi's cryptographic signature on the permission slip itself before calling LedgerApi?
   A: Two reasons stacked together: building that check needs a new code library, and adding a new library needs the owner's sign-off first, so it was correctly left as an open question rather than just added. And since LedgerApi itself doesn't check that signature yet either, verifying it here wouldn't actually change what happens next — so skipping it for now costs nothing real today.
5. Q: A test found that the placeholder developer credentials in this project's config wouldn't actually work if you tried them. Why wasn't that treated as a bug?
   A: Because the code never claimed they would — a comment in the file did, incorrectly, and that comment got corrected. The actual behavior (refusing a request from a key that doesn't match anything configured) was working exactly as intended the whole time; the only real issue was documentation that overpromised, not security that underdelivered.

**One thing that nearly went wrong:** The most convenient way to verify this service's calls to its two sibling services would have been to just trust that the request and response shapes matched what the design document described. A careful second check — reading the siblings' actual code directly rather than their design docs, which can drift out of date — is what catches the exact kind of bug that compiles cleanly, passes every test, and then fails the moment it talks to the real thing: a field renamed, a type changed, a required value that became optional. Nothing like that turned up here, but the check existed specifically because that's the failure mode worth actually hunting for, not assuming away.

### 2026-10-18: Reversal authorization built (Garbati.IdentityApi, PR #4)
**In plain words:** This is the code behind the design decided a few hours earlier. A trusted internal "ops" caller — never a regular customer — can now ask IdentityApi to authorize reversing a transaction, tagged with a short reason (duplicate, technical error, fraud, customer request, or unauthorized). The request skips every customer/mandate check a normal transfer needs, by design, and reuses the exact same signed-permission-slip machine already built for transfers. A second, smaller endpoint lets that same ops caller later report whether the money actually came back or had to be written off.

**Five interview questions:**
1. Q: This endpoint reuses the exact same URL as an ordinary transfer request. How does the code decide which internal permission to check?
   A: It looks inside the request body — is this marked as a reversal or not — rather than deciding from the URL the way almost every other endpoint in this codebase does. That's unusual enough that it got its own named, carefully tested exception to an existing rule that checks every endpoint has one clear, fixed permission, so the exception couldn't accidentally weaken that rule for anything else.
2. Q: Why does a reversal on a joint account that normally needs three people's agreement not need any of their agreement here?
   A: Because that decision was never this endpoint's to make in the first place — by the time a reversal reaches IdentityApi, an ops team has already decided it should happen through their own process. A test proves this directly: the exact same account, built three different ways (no mandate at all, one holder, three holders), gets identical results for a reversal request every time.
3. Q: A reason code was sent as lowercase instead of uppercase. What happens?
   A: It's accepted either way, but it's converted to the standard uppercase form before being saved or placed in the signed permission slip — not left exactly as typed. Reviewing this caught and fixed a real rough edge: without that conversion, a future system comparing codes exactly would have silently missed a validly-submitted lowercase version.
4. Q: What stops someone from recording a reversal's outcome twice?
   A: The second attempt is rejected outright — by an explicit check in the code, and, as a backup, by a database rule that physically refuses to store two outcomes for the same decision even if two requests arrive at the exact same moment.
5. Q: Why does this task feel so much smaller than the joint-account approval work from earlier the same day?
   A: Because it deliberately reuses machinery that already exists instead of building something new — the design decision made just before this avoided an entire category of new complexity (tracking multiple people's approvals) by routing that responsibility to a different, not-yet-built system entirely.

**One thing that nearly went wrong:** The easy, much-shorter way to build this would have been to protect the new reversal action with the same single permission the rest of the authorization endpoint already uses — it would have worked, compiled, and probably passed a casual read. The actual requirement was stricter: the one real team meant to use this must never also be handed the everyday "approve a transfer" permission, and the two must be genuinely exclusive, not just nominally separate. Proving that exclusivity in both directions — and doing it without quietly weakening the existing rule that checks every single endpoint has exactly one clear permission — took deliberately adversarial testing, not just reading the code and assuming it was right.

### 2026-10-18: Reversal authority designed (Garbati.IdentityApi `docs/DESIGN.md`, no PR — a design decision round)
**In plain words:** Earlier work deliberately left one thing undesigned: who's actually allowed to reverse a transaction, and what IdentityApi has to check before allowing it. The answer turned out to be much simpler than expected, because of one architectural rule that already existed: ordinary customers never talk to IdentityApi directly — they always go through a channel app, which goes through the orchestrator. Applying that same rule to reversals means a reversal request only ever comes from one trusted, internal "ops" source — not a customer clicking a button. Whatever back-and-forth approval that internal team needs before deciding to reverse something happens entirely outside IdentityApi, in tooling that doesn't exist yet. By the time IdentityApi sees the request, that decision is already made — so IdentityApi doesn't need to build a second "collect everyone's approval" system like the joint-account one; it just checks the caller is who it claims to be, records a reason, and reuses the exact same signed-permission-slip mechanism already built for ordinary transfers.

**Five interview questions:**
1. Q: Does a reversal of a joint account's transaction need the same number of people to agree as the original transaction did?
   A: No — reversal entirely skips the account's own approval rules, regardless of whether it's a single-holder or joint account. The reasoning: by the time a reversal reaches IdentityApi, an internal team has already decided it should happen, through their own separate process. Re-checking the customer's approval rules on top of that would just be asking the same question twice, through a system that was never meant to answer it for this situation.
2. Q: Why doesn't IdentityApi build its own "two people have to approve this reversal" system, the way it did for joint accounts?
   A: Because that decision already gets made somewhere else — inside a separate internal tool for the operations team, which isn't part of what's being built here. Building a second approval system inside IdentityApi would just duplicate work that already happens upstream, for no real benefit.
3. Q: What's a "reason code," and why borrow existing ones instead of inventing new names?
   A: It's a short, standard label attached to a reversal explaining why it's happening — "duplicate," "technical error," "fraud," and so on. Real international payment systems (ISO 20022) and card networks already agree on almost the same handful of categories, so reusing their names means GARBATI doesn't have to explain a brand-new vocabulary to anyone who already knows how banking disputes work.
4. Q: What happens when a reversal fails because the money's genuinely gone — the recipient already spent it?
   A: IdentityApi records that outcome as its own distinct event, separate from the original reversal attempt — essentially "this is now being treated as a loss, not something we're still chasing." It's a deliberately thin record of that decision, not an attempt to build the actual debt-collection or recovery process, which stays completely outside this piece of the system.
5. Q: Does IdentityApi enforce any deadline on how fast a reversal must happen?
   A: No, on purpose. Since the decision to reverse already happened before IdentityApi is even called, there's nothing left for it to time-limit — it just timestamps the request like it does everything else. Any real speed target is something the operations team is measured against separately, not a rule written into this code.

**One thing that nearly went wrong:** The first pass at this research assumed reversal authorization would need its own version of the joint-account approval machinery — tracking partial approvals, timeouts, and so on — because that's the shape every real-world source described. It took the owner pointing out a simpler existing architectural rule (customers never call IdentityApi directly) to see that applying it consistently made almost the entire approval-collection problem disappear for this specific case — not because the problem doesn't exist, but because it had already been solved by a rule that was sitting there the whole time, just not yet applied to this situation.

### 2026-10-18: IdentityApi joint-account multi-approval workflow (Garbati.IdentityApi, PR #3)
**In plain words:** This finishes the "joint account" feature that earlier work left room for but didn't build. An account can now require more than one person's agreement before a debit happens — "any 2 of 3 holders," for example — the same underlying idea banks call "maker-checker" and crypto wallets call "multisig." Requesting a debit on such an account opens a waiting request; the requester's own approval counts as the first one; other holders approve through the same endpoint until enough people have said yes, at which point the same signed "permission slip" from the previous piece gets issued, exactly as before. A waiting request that nobody finishes in an hour simply expires. Changing how many approvals an account requires is its own, stricter process — it needs *every* current holder's agreement, not just enough to meet today's rule, specifically so two people can't quietly gang up to lower the bar on a third.

**Five interview questions:**
1. Q: Two holders both try to be the one who completes a 2-of-3 request, at the exact same moment. What actually happens?
   A: Only one of them can win. The system locks the request the instant it starts checking "are we done yet?" — using a real database lock, not just a check in application code — so the second holder's attempt has to wait its turn, then re-checks and correctly sees the request is already finished. Without that lock, both could have raced ahead on stale information and both gotten a valid permission slip for what should have been one decision — and that's exactly the bug a test caught and proved, before and after the fix.
2. Q: If a joint-account holder gets their account closed while they still have an outstanding, unfinished approval sitting on a request, does that approval still count later?
   A: No. There are two separate safeguards: one cancels their approval the moment they're revoked directly, and a second, independent one re-checks every contributing approver's status fresh, right at the instant a request would actually be completed — regardless of which path revoked them. Both were tested, including by actually closing a customer for real in the test (not just faking the effect) and confirming the request still correctly refuses to complete.
3. Q: Why does changing an account's required-approval count need everyone's agreement, rather than just enough people to meet today's rule?
   A: Because the looser version has a real loophole — on a "2-of-3" account, two people could agree between themselves to drop it to "1-of-3," permanently cutting the third person out of ever having a say again. Requiring every current holder closes that specific hole.
4. Q: There's no background job checking for expired requests. How does an hour-old, unfinished request actually stop being usable?
   A: The expiry isn't checked on a timer — it's checked the moment anyone next interacts with that specific request, whether that's a status check or a new approval attempt. At that exact moment, if it's past its deadline, it gets marked expired before anything else happens. So it can never be approved late, even though the "expired" label itself might not get written until someone actually looks.
5. Q: This feature could have been built into the very first authorization endpoint instead of as a separate follow-up task. Why split it out?
   A: Because it's a genuinely different, harder problem — tracking partial progress across multiple people, a waiting window, and what happens if someone's standing changes mid-wait — and building it halfway alongside the simpler single-person case would have risked getting both wrong at once. Keeping the original single-approval path completely untouched (verified by a zero-line difference in its existing tests) was the proof that splitting it out worked as intended.

**One thing that nearly went wrong:** The first version of this feature had a real, reproducible bug: two people approving a request at the same instant could each walk away with a valid, independently-signed permission slip for a request meant to be settled once. It wasn't caught by reading the code carefully — it took an actual test that fired two real approvals at the same time against a real database to expose it, run several times to rule out a fluke, and then run again after the fix to prove the fix actually held. A separate concern raised about this same PR — that closing a customer's account might not properly cancel their pending approval — turned out, on direct testing, to already be covered by a second safety net. The lesson from both: a plausible-sounding concern and a real bug look identical from the outside until something actually runs the scenario.

### 2026-10-17: IdentityApi mandates + authorization grant issuance (Garbati.IdentityApi, PR #2)
**In plain words:** This is the piece that actually connects a customer to a bank account and lets them move money. A "mandate" is a record saying "this specific customer may do this specific thing on this specific account" — and, new here, an account can now have more than one mandate holder (a joint account), though the "everyone has to agree" approval logic for that is still a separate future task. When a customer requests something, the system checks their standing, their mandate, and their permission, then — if everything's in order — hands back a small, cryptographically signed "permission slip" (valid for 30 seconds) that a future orchestrator will present to the ledger to actually move the money. This PR also finished a piece the previous one deliberately left undone: closing or marking a customer deceased now actually revokes their mandates and flags solely-held accounts to be frozen.

**Five interview questions:**
1. Q: Why is the one-active-mandate-per-(customer, account) rule a database constraint instead of just a check in the code?
   A: Two requests arriving at the exact same moment could both pass an "is there already one?" check before either has actually saved anything, and both succeed — a race condition. A database constraint is enforced by Postgres itself as the row is written, so even simultaneous requests can't both win; this was actually tested by writing directly to the database with raw SQL, bypassing the application code entirely, and confirming Postgres still rejects the second one.
2. Q: Why does the signed grant expire in 30 seconds, and what's the accepted downside of that?
   A: It's meant for one single, immediate machine-to-machine handoff, not something a person holds onto — a short lifetime limits how long a leaked grant could possibly be useful. The accepted downside: if someone's access is revoked in that exact 30-second window after a grant was already issued, that already-issued grant could in theory still be used. That's a deliberately accepted small risk, not an oversight — and it's the same trade real OAuth systems make with short-lived access tokens.
3. Q: A dev-only signing key is committed openly in the repo. What stops that from accidentally being used for real, in production?
   A: A startup check compares the actual key material (not just its label) against the known dev and test keys, and refuses to even start the app if it's running in Production and that match is found. It checks the real cryptographic key rather than its name specifically so that simply renaming the key couldn't sneak past the check.
4. Q: While fixing a flagged concurrency concern, a real bug turned up that wasn't part of the original ask. What was it, and what does that say about the review process?
   A: Making the signing code thread-safe surfaced an actual crash under concurrent load: the signing library was internally caching something tied to a label that gets reused across every signing call, and that cache ended up pointing at an already-cleaned-up key. It only turned up because the fix included a real test that fires many signing calls at once — exactly why "this is probably fine" isn't treated as equivalent to "a test proves this is fine" on this project.
5. Q: This PR sets every account's approval requirement to exactly 1. If a future task allows 2 or 3, does anything built here silently break?
   A: No — the authorization code has one explicit check that the requirement is exactly 1, and treats anything else as a request it must refuse, not something it tries to handle. So when real multi-person accounts show up later, this code correctly says "not my job" for those instead of quietly doing the wrong thing.

**One thing that nearly went wrong:** The owner conditionally approved committing a real (if dev-only) private signing key into a public repository — approved specifically on the condition that a safety check would stop it from ever running in production. The first version of the pull request committed the key but never actually built that safety check. QA caught this specifically, as a Blocker, not a passing nitpick — the rule here is that a conditional "yes" is only a "yes" once the condition is actually verified to exist, not just remembered as a good intention.

### 2026-10-16/17: IdentityApi foundation — Customer, KYC (Garbati.IdentityApi, PR #1)
**In plain words:** This is the first real code for GARBATI's identity service — everything before this was just a design document. It lets you create a customer record and move them through KYC (know-your-customer) verification: `Pending` → `Verified`/`Rejected`, plus a tier. It deliberately does not yet let a customer actually operate a bank account — that needs "mandates," which don't exist in code yet (the next task builds those). A customer's sensitive details (name, contact info) live in their own separate table from the ordinary status/KYC record, and there's no column at all yet for a government ID number like a BVN or NIN, because nobody has decided how to encrypt one safely — rather than guess, that column simply doesn't exist until someone makes that call properly.

**Five interview questions:**
1. Q: Why does creating a customer need an idempotency key, the same way LedgerApi needs one to create an account?
   A: If a network call times out, the caller (the Orchestrator) doesn't know whether the customer actually got created or not — retrying blindly could create a second customer for the same person. A client-chosen key lets a retry safely ask "did this exact request already happen?" and get back the same answer instead of a duplicate.
2. Q: If the exact same create-customer request is retried with the same key, what happens? What if the key is reused but the details are different?
   A: Same key, same details: you get back the customer that was already created, not a new one. Same key, different details: it's rejected outright (409), because something has gone wrong — a client shouldn't be allowed to quietly "change its mind" about what a given key meant.
3. Q: Why do `suspend`/`reactivate` succeed quietly on a repeat call, but `close`/`mark-deceased` return an error the second time?
   A: Suspend and reactivate are reversible, so repeating one is harmless — it's treated as "already in that state, nothing to do." Close and mark-deceased are permanent, one-way doors; silently accepting a second attempt (possibly for a different reason) could hide something worth a human's attention, so it's refused instead.
4. Q: The design says closing a customer should automatically revoke their account access. Does this code do that?
   A: No, on purpose. "Mandate" — the thing that actually links a customer to a bank account — doesn't exist in the code yet; it's the very next task. This PR changes the customer's status and writes an audit record of that change, and leaves a clearly commented, empty method exactly where the real revocation logic belongs, with a test that proves today's behavior (writing nothing) so the gap can't be silently forgotten.
5. Q: How do we know a lookup for a customer's details can never accidentally return something sensitive like a BVN or NIN?
   A: Two separate reasons stack up: the response object simply has no field to put that information in (not a filter that could have a bug — there's structurally nowhere for it to go), and on top of that, there's no BVN/NIN column in the database at all yet, because nobody has decided how to store one safely.

**One thing that nearly went wrong:** While reviewing the builder's follow-up work, a real bug surfaced in this coordinator's own earlier writing, not the builder's: the IdentityApi design document's prose kept citing decision numbers that didn't actually match its own decisions table — "decision #20" was used in one place for "the channel owns login" and in another for a completely unrelated joint-account rule, and this pattern repeated roughly fifteen times throughout the document. The builder caught it, correctly declined to guess at a fix, and flagged it plainly instead. Since assigning decision numbers is explicitly the coordinator's job, it got fixed by re-deriving the correct number for every citation from the table itself (the one part of the document that was never wrong) rather than by guessing or leaving it for later.

### 2026-10-16: OrchestratorApi minimal design ratified — account opening + plain transfer (garbati-platform, no PR — a design decision round)
**In plain words:** The Orchestrator's whole job is to be the "traffic cop" that calls other services in the right order so nobody forgets a step. The original plan was to demo it running a transfer with a fee attached and the ability to reverse a transfer. Both got cut — not because they're hard, but because the pieces that would make them *correct* don't exist yet: nobody has built the service that computes fees (ProductApi), and nobody has decided who's even allowed to reverse a transaction (that got deliberately left undesigned, tracked separately). Building either one anyway would mean inventing a money rule inside the wrong component, just to make a demo look more impressive. The version that got designed instead does exactly two things end to end: open an account (a four-step sequence across two services) and move money between two accounts with a real authorization check in front of it.

**Five interview questions:**
1. Q: Why does opening an account need its own database table in the Orchestrator, when a transfer doesn't?
   A: Opening an account is four steps across two different services with no way to wrap them in one database transaction — if step 3 succeeds and step 4 fails, something has to remember that, so a retry fixes only the broken step instead of redoing everything or leaving the account stuck. A transfer is one quick round trip where both services involved are already self-protecting against being run twice, so there's nothing extra for the Orchestrator to remember.
2. Q: If the account-opening sequence is retried after a partial failure, how does it avoid redoing the steps that already worked?
   A: Every downstream call gets a unique ID derived from the operation's own ID (e.g. "this operation's create-customer step"), not a random one each time. Retrying sends the exact same ID for a step that already finished, and the other service recognizes it and just hands back what it already did instead of doing it again — the same trick already used elsewhere in this project for keeping a retried payment from happening twice.
3. Q: The design says IdentityApi still issues a real authorization token for every transfer, but LedgerApi doesn't check it yet. Isn't that pointless?
   A: Not pointless — it exercises the real decision-making step (did IdentityApi actually say yes?) so that part of the system is genuinely built and testable now, rather than faked. The only piece missing is LedgerApi double-checking that token itself before posting, which simply doesn't have anywhere to plug that check in yet. Adding it later means adding one field and one check — nothing about how the rest of the flow works has to change.
4. Q: Why doesn't funding an account go through any authorization check?
   A: Because "funding" in this demo isn't a real customer handing over their own money through a real external payment system — it's a stand-in for money entering the ledger from outside, which the ledger already documents as a mock, test-only action. There's no real customer decision to authorize here, so there's nothing for IdentityApi to weigh in on.
5. Q: What's the single biggest thing a reader should NOT assume works in this design, just because it's written down?
   A: That a "customer" in this demo is really authenticated. The Orchestrator currently just trusts whatever customer ID it's handed in the request — there's no real login system behind it yet. That's the exact same gap already flagged, unsolved, in IdentityApi's own design: nothing here pretends to have solved it.

**One thing that nearly went wrong:** It would have been easy to just keep the original "transfer with fee, then reverse it" demo plan and quietly improvise a fee calculation and a reversal rule inside the Orchestrator to make it work, since both are technically easy to code. Catching that this would mean inventing money-affecting rules in a component whose entire design principle is "it decides nothing, it only calls the right things in order" — and asking instead of just building it — is what kept the demo honest about what's actually been decided versus what's just convenient to fake.

### 2026-10-16: IdentityApi design v2 ratified — authorization tokens and joint accounts (garbati-platform, no PR — a design decision round)
**In plain words:** Before any of IdentityApi gets built, its design draft needed to go from "here's a recommendation" to "here's what we're actually building." The draft's core idea: IdentityApi decides whether a customer is allowed to do something, and proves that decision to LedgerApi with a small, signed, 30-second ticket (a token) that LedgerApi checks itself — no phone call back to IdentityApi for every transaction. Research (checked against real security standards — RFC 8725, RFC 9068/7009, OWASP) confirmed this token design matches established practice closely. Three real gaps got closed (what happens when a customer dies or closes their account, who's allowed to freeze an account, and committing to a real database rule instead of a "we should probably check this" comment), and mid-conversation the scope grew: GARBATI will support **joint accounts**, which needed its own research into how banks ("maker-checker"), crypto wallets ("multisig"), and business software ("dual approval") all solve the same underlying problem — requiring more than one person's agreement before something important happens.

**Five interview questions:**
1. Q: Why does LedgerApi check the authorization token itself instead of calling IdentityApi every time to ask "is this really allowed?"
   A: Calling back every time would make LedgerApi depend on IdentityApi being up and fast for every single transaction. Instead, IdentityApi signs a token with a private key only it holds; LedgerApi just checks that signature locally with the matching public key — the same trick OAuth2's JWT access tokens use so a resource server doesn't have to call the authorization server on every request.
2. Q: If a mandate gets revoked right after a token was already issued, can that token still be used?
   A: Yes, for up to the token's remaining lifetime (at most 30 seconds) — this is a deliberately accepted trade-off, not an oversight. The alternative (instant revocation) would require checking back with IdentityApi on every transaction, which is the exact cost this design is avoiding. Keeping the token's life short is what keeps that exposure window small instead of leaving it open-ended.
3. Q: What's the real difference between "any one holder can act alone" and "any two of three holders must agree," and why does it matter who's allowed to change that rule later?
   A: It's a straight trade between convenience and safety — fewer required approvers means faster, easier access; more required approvers means no single person can move money alone. The reason changing that rule needs *everyone's* agreement (not just enough people to meet today's rule) is to stop a subset of holders from quietly weakening an account's protection — two holders out of three lowering the bar to "any one" without the third person ever finding out.
4. Q: A joint-account holder approves a pending debit, then that holder gets suspended before the second approval comes in. What happens to their approval?
   A: It's thrown away immediately, not kept "banked" for later. This matches a real documented mistake in multi-signature crypto wallets, where a removed signer's old approval can wrongly keep counting if the system doesn't explicitly check for that case — so GARBATI re-checks every remaining approver's status again right at the moment the required number is finally reached, not just when each person originally approved.
5. Q: Why does the design explicitly avoid caching a "yes, this is allowed" answer?
   A: Because a cached "yes" from a minute ago could be wrong right now — the mandate might have just been revoked. The 30-second token is already the system's one accepted exception to "always check fresh"; adding a second cache on top would quietly reopen the exact staleness risk the short token lifetime was designed to close.

**One thing that nearly went wrong:** Partway through confirming decisions, a yes to "support joint accounts now" directly contradicted a decision made minutes earlier — a database rule enforcing exactly one active mandate per account, which joint accounts need to break by definition (two or more people, same account). It would have been easy to let both stand and only discover the contradiction once someone tried to build it. Catching it required actually holding both answers in mind at once and flagging the conflict before writing either one down, rather than recording agreement-by-default.

### 2026-10-16: Fee-income and tax-payable system accounts (LedgerApi, PR #28)
**In plain words:** The chain feature (decision #45, above) can post a Fee or Tax leg, but until now it could credit *any* system account — there was no dedicated place for fee income or tax owed to actually land. This change creates exactly those accounts: one Fee Income account and one Tax Payable account per currency (40 accounts total for the 20 currencies GARBATI supports), the same way the existing "funding" accounts were created for deposits and withdrawals. It also adds a safety check: the app refuses to start if any supported currency is missing one of these accounts in configuration. Importantly, nothing *uses* these accounts yet — a chain's fee leg still doesn't know they exist. This PR only builds the destination; routing real fees and tax to it is later work for the orchestrator/ProductApi.

**Five interview questions:**
1. Q: If a 21st currency gets added later but someone forgets to configure its fee-income account, what happens?
   A: The application won't start at all. A startup check runs through every supported currency and fails immediately, by name, if any currency's fee-income or tax-payable account isn't configured — so the gap is caught before the app is live, not discovered later when a fee needs to post.
2. Q: Does a chain's Fee leg have to credit this new Fee Income account specifically?
   A: Not yet. The chain-posting rule from decision #45 only checks "is this a System account," not "is this the *right* System account." These new accounts exist and are configured, but nothing currently points a transaction at them — that's deliberately left for whichever future service (the orchestrator, using ProductApi's rules) actually decides where a fee should go.
3. Q: Why two separate account number ranges (`200000001` for fee income, `300000001` for tax payable) instead of one shared range?
   A: So they can never collide with each other, with the existing funding accounts (`100000001`), or with any customer account, and so each type is instantly recognizable just from its number.
4. Q: Why one migration this time, when the original funding accounts were seeded across two separate migrations?
   A: The funding accounts needed two migrations only because the list of supported currencies itself grew over time — four currencies at first, sixteen more added later. That currency list is already finished at 20, so there was no reason to split this into installments.
5. Q: Is there any money-safety risk in this change?
   A: No — these are brand-new accounts with no balance, and nothing posts to them yet. The actual money-safety rules (balance checks, locking, reversal) all live in the chain-posting code from decision #45, which this PR deliberately did not touch.

**One thing that nearly went wrong:** It would have been easy for the builder to "helpfully" wire these new accounts straight into the chain-posting logic while already in that part of the codebase. The task explicitly forbade this (that routing decision belongs to a future service, not to LedgerApi), and QA specifically checked for it — confirming via a direct code diff that the chain-related files were untouched, and that the new configuration classes aren't read anywhere outside their own tests. Scope discipline, not cleverness, was the thing being tested here.

### 2026-10-16: Chains of legs (LedgerApi, PR #26 + #27)
**In plain words:** Before this, every money movement in the ledger was exactly one debit and one credit — a transfer. But a real transfer often needs to also take a fee, and tax on that fee, as part of the *same* all-or-nothing operation: either the transfer, the fee, and the tax all happen, or none of them do. A "chain" is just an ordered list of up to 10 of these two-entry movements (called "legs") that the ledger posts together inside one database transaction. A plain transfer is just a chain with one leg, so nothing that existed before had to change.

**Five interview questions:**
1. Q: Why is each payer's balance checked once at the start of the chain instead of before every leg?
   A: So the customer gets one clear answer ("insufficient balance") covering everything they're paying in the chain — principal plus fee plus tax — instead of the principal succeeding and the fee failing separately, which would be confusing and leave a half-finished-looking result.
2. Q: Two chains run at the same time, touching the same two accounts in opposite directions. What stops them deadlocking?
   A: Before posting anything, each chain locks every account it's about to debit, once each, always in the same fixed order (ascending account number — not the order the legs happen to be listed). Since every chain agrees on that order, one chain always gets there first and the other just waits, instead of each one holding a lock the other needs.
3. Q: If the second leg of a three-leg chain fails, what happens to the other two?
   A: Nothing from any leg is kept — the database throws away the whole attempt, as if it never happened. Then a separate, second save records that the chain failed, on which leg, and why, so a retry with the same idempotency key returns that stored failure instead of silently trying again.
4. Q: Why does reversing a chain undo tax, then fee, then the principal — backwards from how it was posted?
   A: The fee and tax only exist because of the principal, so logically they get undone first. It also means if undoing the principal fails partway (say the recipient already spent it), the whole reversal rolls back together — you can't end up in a state where the fee was refunded but the principal wasn't, or vice versa.
5. Q: Why is a client blocked from using an idempotency key that starts with `chain:`?
   A: The ledger generates its own keys in that exact shape (`chain:{chainId}:{sequence}`) for the individual legs inside a chain. If a customer-chosen key could also look like that, there's a theoretical risk of two different things colliding under the same key, so it's simplest to just forbid that prefix everywhere a client supplies their own key.

**One thing that nearly went wrong:** This feature was actually built and merged straight to `main` (PR #26, then a follow-up fix in PR #27) *before* the task-board/QA process in this repo existed. It worked and CI passed, but there was no written QA review and no learning-log entry — exactly the kind of silent gap the process is meant to prevent. The coordinator caught this by reading the task file (which already had a builder's self-audit note at the bottom), ran an independent QA review against the merged code anyway, and asked the owner to formally ratify the choices that had already shipped (leg types limited to Principal/Fee/Tax, 10-leg max, a failed reversal cancels the whole thing, a reversal gives back the spending limit) rather than rubber-stamping it. QA also caught one real documentation bug: `ARCHITECTURE.md` still listed a `decision_id` column as part of this feature's data shape, but that column actually belongs to a *different*, not-yet-built decision (#47, the security token) — now fixed in the doc.

### 2026-10-16: Service boundaries ratified — P-1 to P-6 (garbati-platform, no PR — a documentation decision)
**In plain words:** `ARCHITECTURE.md` draws the map of which future service does what: a traffic-cop `OrchestratorApi` that runs the steps of a transaction in order; a `ProductApi` that only *decides* fees/rules while the orchestrator is the only thing that actually *moves* money through `LedgerApi`; a `ScheduleApi` for recurring payments; no service ever reading another's database directly; and, for now, fewer deployed services than designed services to save cost. Before locking these in, a researcher checked each one against real, named industry patterns rather than taking the recommendation on faith.

**Five interview questions:**
1. Q: What is a "Saga" in distributed systems, and which style did GARBATI pick?
   A: A Saga is how you keep a multi-step operation consistent when it spans several services that each have their own database — instead of one big database transaction, each step commits on its own, and if a later step fails, earlier steps are deliberately undone by code written for that purpose (a "compensating transaction"), not automatically by the database. GARBATI picked the **orchestration** style: one component (the Orchestrator) is in charge of calling every step in order, rather than services reacting to each other's events with nobody in overall charge (**choreography**).
2. Q: Why split "who decides the fee" (ProductApi) from "who actually posts it" (via the Orchestrator, to LedgerApi)?
   A: So the two can change independently — pricing changes constantly and shouldn't need a ledger release, and real core-banking vendors (Temenos, Mambu) draw this same line between a product/pricing engine and the posting engine. If the ledger absorbed pricing logic, every product tweak would risk touching the one piece of code that must stay simple and trustworthy.
3. Q: What's the real cost of "no shared database between services," and is it worth it?
   A: You lose the easy stuff — a single SQL query that joins data across two services, or one database transaction spanning two services' data. You have to call another service's API instead, and accept that data might be briefly out of sync (eventual consistency). The benefit: each service can change its own schema without breaking anyone else, and for a ledger specifically, nobody else can quietly corrupt its one authoritative copy of the truth.
4. Q: GARBATI is designing four services but deploying only two for now. Is that a shortcut that will bite later?
   A: It's a recognized approach (Martin Fowler's "monolith first" / modular monolith) — build with clean internal boundaries, deploy fewer actual running services while the system is small, split later once there's a real reason. The honest caveat, straight from Fowler: splitting it later isn't guaranteed to be easy — it only stays easy if the "no shared database, API-only" discipline is actually followed in the code the whole time, not just on paper.
5. Q: Did the research prove GARBATI's design is correct?
   A: No — it proved the design isn't inventing anything unusual; each piece has a name and documented trade-offs elsewhere. It didn't (and couldn't) prove GARBATI specifically will work out, and it explicitly doesn't touch Sharia-compliance or Nigerian-regulatory questions, which still need a scholar and a compliance officer respectively.

**One thing that nearly went wrong:** The recommendation had already been written into `ARCHITECTURE.md` before this round, and it would have been easy to just ask the owner to rubber-stamp it. Instead, a researcher was sent to check each of the six proposed boundaries against real, citable sources first (Martin Fowler, microservices.io, Microsoft's own .NET architecture guide, Azure/AWS architecture docs) — confirming they match standard practice rather than trusting the plan on paper. That surfaced one real gap worth tracking: standing orders in the real world are usually *not* auto-retried on failure (unlike direct debits), which GARBATI's `ScheduleApi` design (not built yet) will need to decide explicitly — now recorded as an open question in `ARCHITECTURE.md` Section 9 rather than silently assumed.
