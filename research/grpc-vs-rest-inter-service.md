# gRPC vs plain HTTP/JSON for GARBATI's inter-service calls

**Task:** T-023. **Status:** Research only — no code, no decision. Answers a question the owner raised, does not recommend building anything.
**Scope:** OrchestratorApi → IdentityApi and OrchestratorApi → LedgerApi, all ASP.NET Core 8 / .NET 8.

---

## Plain-language summary (read this first)

Every term below is defined the first time it's used, because this is written for a learner, not an expert.

Today, when `OrchestratorApi` needs something from `IdentityApi` or `LedgerApi`, it makes an ordinary **HTTP** call — the same kind of request a web browser makes to a website — carrying a **JSON** body (a plain-text format like `{"amount": 500, "currency": "NGN"}`) and an API key header. This is sometimes called "REST" (a style of designing HTTP APIs), though GARBATI's own docs just call it "plain HTTP/JSON."

**gRPC** is a different way for two programs to talk to each other. Instead of JSON text, it sends data as **Protocol Buffers** ("protobuf") — a compact binary format (binary means the data is packed as raw bytes designed for computers to read quickly, not as readable text) defined in a `.proto` file, which is a contract that says exactly which fields exist and what type each one is. gRPC always runs over **HTTP/2**, a newer version of the HTTP protocol that can send many requests over one connection at the same time (called **multiplexing**) instead of one-at-a-time, which avoids a slowdown called **head-of-line blocking** (one slow request blocking others behind it on the same connection).

A simple analogy: plain HTTP/JSON is like mailing a handwritten letter — anyone can read it without special tools, but it takes longer to write and more paper (bytes) to say the same thing. gRPC is like sending a pre-agreed, numbered punch-card — much smaller and faster to produce and read, but you need the matching punch-card reader (the generated client/server code from the `.proto` file) to make sense of it, and a human glancing at the card alone can't read it.

**Short answer to the owner's question:** gRPC genuinely is faster than JSON-over-HTTP/1.1 in published benchmarks, mainly because of the smaller binary payload and HTTP/2's multiplexing. But at GARBATI's current and near-future scale (a handful of synchronous calls per customer operation, not thousands of requests per second), the latency difference is unlikely to be the thing standing between GARBATI and a faster product — and some published studies actually found plain REST *faster* at low traffic and small payloads, the opposite of what people usually assume. Adopting gRPC today would also cost GARBATI something concrete: it is both an **API contract change** and **a new dependency**, both of which `AGENTS.md` names as human-only gates, and it would complicate the Swagger-based demo story the whole platform's recruiter-facing strategy currently depends on (the tool that generates Swagger docs *from* gRPC, `Microsoft.AspNetCore.Grpc.Swagger`, was deprecated and removed by Microsoft in 2026 — see Q3/Q5 below). The lighter alternatives in Q5 (connection reuse, compression) likely close most of the real-world gap without any of that cost.

## Q1. What is gRPC, in plain terms, and how much faster is it really?

**gRPC** is a **remote procedure call (RPC)** framework — a way of calling a method on another program over the network that looks, from the calling code's point of view, almost like calling a local method. It was built by Google and is now an open, cross-language standard ([grpc.io](https://grpc.io/docs/what-is-grpc/introduction/)).

Three pieces make it work:
1. **`.proto` files** — a contract file, in a small language called Protocol Buffers, that lists the service's methods and the exact shape of each message (field names, types, and numeric "tags"). A compiler (`protoc`) turns this file into generated client and server code in whatever language you need — so in C# you get a real typed class with real typed methods, not a URL string you build by hand.
2. **Protobuf binary serialization** — **serialization** is the general process of turning an in-memory object into bytes that can be sent over a network (and deserialization is turning bytes back into an object). JSON does this as human-readable text (`{"amount":500}`); Protobuf does it as compact binary — numbers and field identifiers packed as raw bytes with no field names repeated on the wire, so it is both smaller to send and faster to parse.
3. **HTTP/2** — gRPC always runs over HTTP/2, which supports **multiplexing** multiple in-flight requests over one TCP connection, and uses binary framing and header compression, both of which make it more efficient than HTTP/1.1 ([Microsoft Learn, "Compare gRPC services with HTTP APIs"](https://learn.microsoft.com/en-us/aspnet/core/grpc/comparison)). Note that HTTP/2 is not exclusive to gRPC — a plain JSON API can also be served over HTTP/2.

**How much faster, with real citations:** this is less settled than marketing claims suggest, and the size of the gap depends heavily on payload size, traffic level, and what exactly is being measured. I deliberately avoided SEO-style benchmark blog posts (several appeared in search results with suspiciously precise headline numbers like "77% faster" with no visible methodology, e.g. tech-insider.org — excluded as low-quality) in favor of published academic comparisons and Microsoft's own docs:

- Microsoft's own official comparison makes only a qualitative claim, not a specific percentage: "a gRPC message is always smaller than an equivalent JSON message," and Protobuf "serializes very quickly on the server and client" ([Microsoft Learn, Compare gRPC services with HTTP APIs](https://learn.microsoft.com/en-us/aspnet/core/grpc/comparison)). Microsoft does not publish a specific "X% faster than REST" number for ASP.NET Core.
- A peer-reviewed-indexed study, "*Comparative Performance Analysis of GRPC and Rest API Under Various Traffic Conditions and Data Sizes Using a Quantitative Approach*" (listed in DOAJ, the Directory of Open Access Journals — [DOAJ listing](https://doaj.org/article/486abcc5283a4af3827300f9904f7a65); full text was behind a 403 wall I could not get past, so the following numbers come from the paper's indexed abstract/summary, not a page I read in full myself) reports the opposite of the usual assumption for **small payloads at low traffic**: REST had *higher* throughput (995 vs. 29.5 requests/minute in their low-traffic test) and a *faster* GET response time (3 ms vs. 20 ms) than gRPC in that condition, while gRPC pulled ahead on large data transfers (276.34 KB/s vs. 134.1 KB/s) and kept more stable latency under load.
- A different study, "*Performance evaluation of microservices communication with REST, GraphQL, and gRPC*" ([ResearchGate listing](https://www.researchgate.net/publication/381763921_Performance_evaluation_of_microservices_communication_with_REST_GraphQL_and_gRPC); again, full text was not accessible to me, only the indexed summary), reports gRPC with lower average response times than REST as concurrent request volume rises — about 79.9 ms vs. 152.56 ms at 100 concurrent requests, and the gap holding (66–68 ms vs. ~150 ms) at 300–500 concurrent requests.
- The community-maintained [`grpc_bench`](https://github.com/LesnyRumcajs/grpc_bench) project (a well-known, actively run GitHub benchmark, not a blog post) measures gRPC implementations against each other across languages — .NET's gRPC implementation performed competitively (tens of thousands of requests/second on modest hardware in various runs, e.g. the [2022-02-19 results](https://github.com/LesnyRumcajs/grpc_bench/wiki/2022-02-19-bench-results)). This is useful evidence that .NET's gRPC stack itself is efficient, but it is **gRPC-vs-gRPC across languages, not gRPC-vs-REST** — I could not find a REST comparison in this project, so don't read it as a REST-vs-gRPC number.

**Honest conclusion for Q1:** the direction of the gRPC advantage (smaller payload, HTTP/2 multiplexing) is real and well documented structurally. The *size* of any resulting latency win is highly dependent on payload size and concurrency, and at least one credible study found REST outperforming gRPC specifically in the small-payload, low-traffic condition closest to GARBATI's current reality. Treat any single-number "gRPC is N% faster" claim with suspicion unless the payload size and traffic level are stated.

## Q2. Does gRPC make practical sense for GARBATI's actual calls today?

GARBATI's current OrchestratorApi → IdentityApi/LedgerApi calls are: synchronous, small JSON payloads (account numbers, amounts, customer IDs — not megabyte blobs), and low fan-out (per `ARCHITECTURE.md` Section 4.1 and the DESIGN.md transfer flow, a handful of calls per customer operation — not thousands of requests per second).

Microsoft's own guidance lists gRPC's recommended scenarios as: microservices needing low latency/high throughput, real-time bidirectional streaming, polyglot (multi-language) environments, and network-constrained environments like mobile apps ([Microsoft Learn, Compare gRPC services with HTTP APIs](https://learn.microsoft.com/en-us/aspnet/core/grpc/comparison)). GARBATI's inter-service calls are same-datacenter, same-language (.NET-to-.NET), not high fan-out, and not streaming — none of gRPC's strongest selling points line up with the current shape of the problem.

The academic evidence in Q1 reinforces this: the DOAJ-indexed study found REST *faster* at low traffic and small payloads — the regime GARBATI is in today — and gRPC's advantage only showing up clearly at higher traffic or larger payloads. A separate indexed study ("*Impact of Protocol Selection on Performance and Scalability in Microservices: A Comparison of gRPC, REST, and GraphQL*," [ResearchGate listing](https://www.researchgate.net/publication/392507557_Impact_of_Protocol_Selection_on_Performance_and_Scalability_in_Microservices_A_Comparison_of_gRPC_REST_and_GraphQL); full text not independently verified by me) is reported to describe gRPC performing best at "low-to-medium loads" but degrading under very high load due to buffer/memory behavior in its underlying networking library — a reminder that "gRPC is always faster" is not a safe universal rule even at the high-traffic end.

**Practical reading:** GARBATI does not have the request-volume or fan-out problem that gRPC is specifically good at solving. This looks like exactly the "solution to a scaling problem GARBATI doesn't have yet" pattern the task description anticipated. The dominant cost in each of today's calls is far more likely to be the database round-trip inside IdentityApi/LedgerApi (checking KYC status, locking and updating ledger rows under `SELECT ... FOR UPDATE` per `ARCHITECTURE.md` Section 12.5) than the few hundred microseconds of difference between parsing a small JSON body and a small Protobuf message. No source found in this research measures that specific bottleneck for GARBATI, because GARBATI has not been profiled — this is inference, not a verified measurement, and is flagged as such.

## Q3. What would adopting gRPC concretely involve in ASP.NET Core 8?

- **Package:** `Grpc.AspNetCore` on the server, `Grpc.Net.Client` on the calling client — both are official Microsoft/gRPC NuGet packages supporting .NET 8 ([Microsoft Learn, gRPC on .NET supported platforms](https://learn.microsoft.com/en-us/aspnet/core/grpc/supported-platforms)).
- **Contracts:** gRPC requires `.proto` files, which is a genuinely different artifact from the OpenAPI YAML files `garbati-platform/contracts/README.md` currently defines as the one-file-per-service contract convention. These would need to live somewhere — most likely alongside the existing OpenAPI files in `contracts/`, since that directory is explicitly described as the home for cross-service contracts, but `garbati-platform/AGENTS.md` is explicit that only the coordinator/owner edits `contracts/`, and a builder only proposes the change in a PR description. This is itself a decision the owner would need to make, not something I'm proposing here.
- **Code generation:** the `.proto` file is compiled by `protoc` (via an MSBuild integration in the `Grpc.Tools` package) into generated C# service base classes, message classes, and a typed client — this happens automatically on build, not as a manual step.
- **Coexisting with REST/Swagger on the same service:** this is possible but not free. Two real paths exist, both from Microsoft's own docs:
  1. **Run gRPC and ASP.NET Core Minimal API/Controller endpoints side by side** in the same Kestrel process, on routes that don't collide — straightforward, well-supported, but it means GARBATI would be maintaining *two* separate API surfaces (the existing REST/Swagger one for the demo, plus a new gRPC one) for the same underlying operation, with no single generated contract covering both.
  2. **gRPC JSON transcoding** (`Microsoft.AspNetCore.Grpc.JsonTranscoding`) lets a single gRPC service also be called as a normal JSON HTTP endpoint, by annotating the `.proto` file with HTTP route bindings ([Microsoft Learn, gRPC JSON transcoding](https://learn.microsoft.com/en-us/aspnet/core/grpc/json-transcoding)). This sounds like the clean answer to "keep Swagger for recruiters while adding gRPC," but there is a real, current catch directly relevant to GARBATI's demo strategy: the companion package that generated Swagger/OpenAPI docs *from* a transcoded gRPC service, `Microsoft.AspNetCore.Grpc.Swagger`, was **deprecated and removed from the ASP.NET Core codebase in 2026** because it had "remained experimental with limited usage and no recent investment" and relied on the older Swashbuckle tooling rather than the newer `Microsoft.OpenApi` tooling the ecosystem has standardized on ([dotnet/aspnetcore GitHub issue #67134](https://github.com/dotnet/aspnetcore/issues/67134), closed via PR #67919). Commenters on that issue noted there is now no first-party replacement, and an independent community fork (`Community.Grpc.OpenApi`) has sprung up to fill the gap — meaning GARBATI would depend on a community-maintained package, not an officially supported Microsoft one, to keep generating Swagger docs for a gRPC-backed endpoint. This is a genuinely new finding worth weighing carefully against the platform's recruiter-facing demo strategy.
- Kestrel (ASP.NET Core's web server) needs explicit configuration to serve both HTTP/1.1 (for REST/Swagger) and HTTP/2 (for gRPC) on the same port, and doing so **requires TLS** for protocol negotiation ([Microsoft Learn, gRPC JSON transcoding — HTTP protocol](https://learn.microsoft.com/en-us/aspnet/core/grpc/json-transcoding)).

## Q4. What do real fintech/banking microservice systems actually do here?

I looked for concrete, verifiable examples rather than generic "microservices" advice:

- **gRPC is a real, production choice in money-moving software**, but the clearest verifiable example I found is from the cryptocurrency/payments space rather than traditional core banking: **LND (Lightning Network Daemon)**, the reference implementation of a Bitcoin Lightning Network payment node, exposes its node-control and payment API as a gRPC service (with a REST option layered on top), documented officially at [lightning.engineering/api-docs/api/lnd](https://lightning.engineering/api-docs/api/lnd/) and in the [lnd GitHub repository](https://github.com/lightningnetwork/lnd). This confirms gRPC is used for real money-moving operations in production, not just toy examples.
- gRPC's own project blog names **Square** (a payments company) among early production adopters when gRPC reached its 1.0 release ([grpc.io blog, "gRPC Project is now 1.0"](https://grpc.io/blog/gablogpost)), alongside Netflix, CoreOS, Docker, and Cisco. This is suggestive that payments companies do use gRPC, though it does not describe Square's specific internal architecture.
- I found several items claiming specific fintech case-study numbers (e.g., a "67% reduction in transaction processing time" and "$2.4 million in annual savings" attributed to an unnamed "FinTech Global Bank") on a marketing-style blog (webskyne.com). I am **not citing those numbers** — the source reads as promotional content without an identifiable company, methodology, or independent verification, which is exactly the kind of low-quality source this research should avoid repeating as fact.
- Several academic papers specifically framing gRPC for "payment systems" and "core banking microservices" exist (e.g., "*The Future of Payment Systems: Transitioning from REST to gRPC for Improved Efficiency and Security*" and "*Microservices Architecture in Fintech: A Case Study on Scalable Loan Processing*," IEEE), but both were behind access walls I could not get past, so I can report their existence and titles but not verify their actual findings firsthand. Treat these as leads for the owner to follow up on directly, not as verified evidence.

**Audit/logging caution (direct answer to the task's specific question):** yes, gRPC's binary format genuinely does make raw request/response logging and manual inspection harder than plain JSON, and Microsoft's own docs say so plainly: "Protobuf requires the message's interface description specified in the `.proto` file to properly deserialize. Additional tooling is required to analyze Protobuf payloads on the wire and to compose requests by hand" ([Microsoft Learn, Compare gRPC services with HTTP APIs — "Not human readable"](https://learn.microsoft.com/en-us/aspnet/core/grpc/comparison)). Microsoft's mitigation is: Protobuf messages can be converted to and from JSON programmatically for logging purposes, and gRPC supports **server reflection** and a **command-line tool** for inspecting binary payloads — but both require deliberate extra tooling that a plain JSON audit trail gets "for free" just by writing the request body to a log. Given `ARCHITECTURE.md` Section 5's existing rule that audit rows are written in the same database transaction as the change they describe (not as raw request/response dumps), this risk is somewhat contained for GARBATI specifically — the audit trail is already a structured record, not a log of the wire bytes — but any future "replay this exact customer request" tooling or support-debugging workflow that currently works by eyeballing a JSON body in a log would need new tooling to do the same thing against Protobuf. A compliance officer should confirm this is acceptable for GARBATI's actual audit and regulatory evidentiary requirements before any contract change is made — I am describing a technical tradeoff, not making a compliance ruling.

## Q5. What are the real downsides, and do lighter alternatives close most of the gap?

**Downsides, concretely:**

- **Azure App Service support is Linux-only.** Microsoft's own supported-platforms doc states plainly: "gRPC requires a Linux-based environment on Azure App Service" ([Microsoft Learn, gRPC on .NET supported platforms — Azure services](https://learn.microsoft.com/en-us/aspnet/core/grpc/supported-platforms)). This matters directly because the task names Azure App Service as where LedgerApi/IdentityApi already deploy — if either is on a Windows App Service plan, gRPC is not a drop-in option there without a hosting change, which is itself a separate decision.
- **Load balancer/proxy compatibility is not automatic.** Microsoft's own gRPC performance guidance warns that L4 (transport-level) load balancers — which distribute by TCP connection — "don't work well with gRPC," because gRPC multiplexes many calls over one connection, so an L4 balancer sends *all* of a client's gRPC calls to one backend instance regardless of load. The fix is either client-side load balancing or an L7 (application-aware) proxy such as Envoy, Linkerd, or YARP, both of which Microsoft explicitly recommends as "an extra option," not something that's automatic ([Microsoft Learn, Performance best practices with gRPC — Load balancing](https://learn.microsoft.com/en-us/aspnet/core/grpc/performance)).
- **Debuggability**, as covered under Q4: no `curl`-and-read-the-JSON workflow without extra tooling (`grpcurl`, server reflection, or deliberate JSON conversion code).
- **Browser limitation:** gRPC cannot be called directly from a browser at all — "It's impossible to directly call a gRPC service from a browser today" because no browser exposes the level of HTTP/2 control gRPC needs ([Microsoft Learn, Compare gRPC services with HTTP APIs](https://learn.microsoft.com/en-us/aspnet/core/grpc/comparison)). This is not directly relevant to service-to-service calls, but it does mean any future browser-based admin tool or Channel UI could never call a gRPC endpoint directly without a gRPC-Web proxy or the JSON transcoding path covered in Q3.
- **Swagger tooling risk**, covered in Q3: the first-party Swagger-from-gRPC package was deprecated in 2026.

**Lighter alternatives that don't require a contract change:**

- **`IHttpClientFactory`** is Microsoft's own recommended way to create `HttpClient` instances in ASP.NET Core, and it already solves two real performance problems without any protocol change: socket exhaustion (creating too many short-lived `HttpClient`/handler instances) and stale DNS (handlers that keep connections open forever and never notice a DNS change). Per Microsoft's own docs, the factory "pools the `HttpMessageHandler` instances created by the factory to reduce resource consumption" and reuses pooled connections (keep-alive) automatically, with no special configuration required beyond registering a typed client with `AddHttpClient<T>()` ([Microsoft Learn, "HTTP requests with IHttpClientFactory"](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/http-requests)). **If OrchestratorApi is already using `IHttpClientFactory`/typed clients to call IdentityApi and LedgerApi (the DESIGN.md's language ("the Orchestrator authenticates to both downstream services as a trusted service client") is consistent with, but doesn't explicitly confirm, this — I could not verify the actual client registration code, see the note under "What GARBATI does today" above), GARBATI likely already gets connection-pooling and keep-alive for free, which closes a meaningful part of the "new connection per call" cost gRPC channel-reuse is also solving (Microsoft's own gRPC performance guide warns that *not* reusing a gRPC channel costs "multiple network round-trips" to redo the TCP/TLS handshake each time ([Microsoft Learn, Performance best practices with gRPC — Reuse gRPC channels](https://learn.microsoft.com/en-us/aspnet/core/grpc/performance)) — exactly the problem connection pooling already solves on the HTTP/JSON side.**
- **Response compression** (e.g., `ResponseCompressionMiddleware` in ASP.NET Core) reduces bytes-on-the-wire for JSON without changing the contract at all, closing some of the "payload size" gap Protobuf wins on — though it adds CPU cost for compress/decompress, so it is a tradeoff, not a free win.
- **HTTP/2 for the existing JSON APIs** is possible without gRPC at all — Microsoft's own comparison doc is explicit that "HTTP/2 is not exclusive to gRPC. Many request types, including HTTP APIs with JSON, can use HTTP/2 and benefit from its performance improvements" ([Microsoft Learn, Compare gRPC services with HTTP APIs](https://learn.microsoft.com/en-us/aspnet/core/grpc/comparison)) — meaning some of gRPC's transport-level advantage (multiplexing, binary framing) is available to GARBATI's current JSON APIs just by enabling HTTP/2 on Kestrel, with zero contract change.

**Honest conclusion for Q5:** the combination of confirming `IHttpClientFactory` is actually in use, enabling HTTP/2 on the existing JSON endpoints, and optionally adding response compression is very likely to close most of the latency gap that matters at GARBATI's current scale, for a small fraction of the cost (no new dependency, no API contract change, no Swagger-tooling risk, no Azure-Linux hosting constraint) of a gRPC migration.

## Recommended path for GARBATI, explained simply

**Recommendation: not yet.** This is a recommendation, not a decision — only the owner decides, per `AGENTS.md`. But the task asked for a walk-through of what trying gRPC would mechanically look like for one call, so a learner can actually picture it. Here is what converting just the OrchestratorApi → LedgerApi transfer call (`POST /api/transfers` today) to gRPC would involve, step by step:

1. **Write a `.proto` file** describing the transfer call as a contract — something like a `TransferService` with one method, `Transfer`, that takes a message with fields for the debit account, credit account, amount, currency, idempotency key, and decision token, and returns a message with the result. This file would need a home — most likely proposed as a new file under `garbati-platform/contracts/`, but only the owner/coordinator can actually add it there (`AGENTS.md`).
2. **Add `Grpc.AspNetCore` and `Grpc.Tools` to LedgerApi**, and `Grpc.Net.Client`/`Grpc.Net.ClientFactory` to OrchestratorApi. Both are new NuGet packages — a new dependency, a human-only gate per `AGENTS.md`.
3. **Let the build generate code from the `.proto` file.** `protoc` (run automatically by the `Grpc.Tools` MSBuild integration) produces a C# base class LedgerApi implements (e.g. `TransferServiceBase`) and a typed client class OrchestratorApi calls (e.g. `TransferServiceClient`) — no more hand-building a JSON object and an `HttpClient.PostAsync` call; instead it becomes something like `await client.TransferAsync(request)`, which looks like an ordinary method call.
4. **LedgerApi implements the generated base class**, moving the existing `TransferService` logic (the checks and database transaction described in `ARCHITECTURE.md` Section 12) behind the new gRPC method instead of (or alongside) the existing `POST /api/transfers` controller action.
5. **LedgerApi registers the gRPC endpoint** (`app.MapGrpcService<TransferGrpcService>()`), and — because the existing REST/Swagger endpoint for the same operation still needs to exist for the recruiter-facing demo — Kestrel needs to be configured to serve both HTTP/1.1 (for REST/Swagger) and HTTP/2 (for gRPC), which requires TLS even in development, per Microsoft's own docs.
6. **Carry over everything the current contract already does**, which is not optional: the API key/scopes, the idempotency key, the correlation ID, and the signed decision token all need an equivalent place in the new `.proto` message or in gRPC's own metadata (gRPC calls support custom headers, similar to HTTP headers, for things like the correlation ID). None of this is automatic just by switching protocols — it has to be deliberately re-built into the new contract, and is exactly the kind of "API contract change" `AGENTS.md` flags as a human-only gate.
7. **Decide what happens to the audit trail.** Since Protobuf messages aren't human-readable on their own, anyone who currently reads a logged JSON request body to understand what happened needs a replacement — either converting the Protobuf message to JSON before logging it, or accepting that raw request bytes are no longer eyeballable without `grpcurl` or a reflection tool.
8. **Test it**, including the specific failure modes GARBATI already cares about: a timeout must still never be treated as approval (`ARCHITECTURE.md` Section 5), and the idempotency guarantee (same key, same result) has to keep working across the new transport.

Doing this for *one* call, while every other call (including LedgerApi's own Swagger-documented REST surface) stays as-is, is realistic as a learning exercise or a spike — but running two parallel API technologies for the same service long-term is real ongoing complexity, and the Swagger/OpenAPI tooling gap found in Q3 means the "coexist cleanly with the demo" assumption needs re-checking before committing to it even as an experiment.
