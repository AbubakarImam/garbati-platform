# Research: what does GARBATI need to be a credible, standard open-source core-banking platform?

Task: T-037. **This document does not decide anything and recommends no specific code.** It benchmarks GARBATI against real comparable open-source projects and lists gaps for the owner to prioritize. Every "needs compliance/scholar confirmation" note below means exactly that — this is a researcher's reading of public documentation, not a ruling.

## Plain-language summary

GARBATI's five services are built with real money-safety discipline (idempotency, audit, maker-checker, QA review) — that part is not in question. What's missing is everything a stranger needs *around* the code before they'd trust it: a license (so anyone can legally use it at all), a place to safely report a security bug, a way to run the whole platform with one command instead of five separate Dockerfiles, a concrete plan for the one dataset that must never be lost (the ledger database), and — specific to a *banking* project — an actual answer for how BVN/NIN will be encrypted once IdentityApi needs to store them for real. I checked the closest real comparison, Apache Fineract (the actively maintained successor to Mifos X, used by 400+ real microfinance institutions), plus three others (Cyclos, Formance Ledger, Lerian Midaz) to see what a credible project in this exact space actually ships versus what's normal to leave to the adopter.

Three things surprised me and are worth the owner's attention up front:
1. **GARBATI already does several things right that many early OSS projects don't**: a PR template exists, both LedgerApi and IdentityApi have genuinely good per-service READMEs (prerequisites, getting-started, project layout), secrets are hash-only and revocable per-demo-visitor, and every prior research brief already models the "I could not verify this, a qualified person must confirm" honesty this exact task demands. This is not a project starting from zero.
2. **The BVN/NIN encryption gap is more absolute than "unencrypted"**: `Garbati.IdentityApi/docs/DESIGN.md` Appendix B confirms the `CustomerIdentityData` table doesn't even have a BVN/NIN column yet — it was deliberately left out "pending a follow-up decision," not built-and-unencrypted. Nothing has regressed; nothing has advanced either.
3. **A new, dated, real regulatory development surfaced during this research that nothing in the repo currently tracks**: CBN Circular PSS/DIR/PUB/CIR/001/004 (15 June 2026) requires Nigeria-originated payment/financial data to be stored and processed *inside Nigeria* by 1 January 2027. GARBATI's one deployed service, LedgerApi, currently runs on Azure App Service in "South Africa North" — not Nigeria. This is unrelated to encryption and is its own, separate, time-bound gap.

Confidence overall: **medium-high** for the benchmark claims (primary GitHub/official-docs sources read directly where possible); **medium** for exact CBN circular scope (secondary legal-commentary sources, consistent with each other but I could not reach the primary CBN PDF); **high** for everything about GARBATI's own repos (read directly).

## Benchmark: what comparable projects actually ship

| Project | Domain fit | License | Governance | Security/vulnerability disclosure | Compliance posture | Single-command local dev |
|---|---|---|---|---|---|---|
| **Apache Fineract** (successor to Mifos X) | Closest direct comparison — open-source core banking/MFI platform, 400+ real institutions | **Apache 2.0** | Apache Software Foundation (meritocratic PMC); no separate company owns it | Dedicated `security@fineract.apache.org`, follows ASF's standard private-then-public vulnerability process, public [security report page](https://fineract.apache.org/security.html) listing every fixed CVE with dates and severity | No PCI-DSS/SOC2/ISO27001 claim found; recognized as a [Digital Public Good](https://www.digitalpublicgoods.net/dpgs-for-dpi/compliance/apache-fineract) (partially meets 14/18 DPI-alignment checks — notably only partial on "Security & Privacy" and "Federation Readiness") | **Yes** — repo ships multiple `docker-compose-*.yml` files (postgresql, mysql, mariadb, development, postgresql-kafka) specifically so a newcomer can run the whole stack |
| **Cyclos** | Named direct comparison — OSS banking/complementary-currency software used by real MFIs | **GPLv2** (copyleft) | Non-profit (STRO) | Not found/verified in this research | Not found/verified | Not verified |
| **Formance Ledger** | General-purpose programmable double-entry ledger, not core-banking-specific | **MIT** (permissive) | Company-backed (Formance) | Not independently verified | Not found | Not independently verified |
| **Lerian Midaz** | Composable core-banking ledger (onboarding, transactions, fees) — close architecturally to GARBATI's multi-service ledger shape | **Elastic License 2.0** — "source-available," **not** an OSI-approved open-source license | Company-backed (Lerian); repo references a `GOVERNANCE.md` I could not independently fetch (404 on direct attempt) | Not independently verified | Not found | Not independently verified |

**Why the license row matters most, concretely:**
- **Apache 2.0** (Fineract) includes an *express patent grant and a patent-retaliation clause* — if a contributor later sues a user over a patent covering their own contribution, they lose their license to the project. This is a real, material protection for an institution building on GARBATI, and it's the reason Apache 2.0 is the default choice for foundation-governed infrastructure software. It also has no copyleft: an adopting bank can run a privately modified fork and never has to publish its changes.
- **GPLv2** (Cyclos) is copyleft: distributing a modified version legally requires offering the modified source under GPLv2 too. Note this is *distribution-triggered*, not *use-triggered* — a bank that runs a modified Cyclos fork purely internally (never distributes the binary to a third party) is not legally required to publish its changes under GPLv2 itself. This is a real, frequently-misunderstood nuance the owner should get confirmed by someone with actual OSS-licensing legal expertise before assuming GPLv2 either is or isn't "safe" for a closed fork.
- **Elastic License 2.0** (Midaz) is deliberately *not* open source by the OSI definition — it exists specifically to stop cloud providers and competitors from reselling the software as a hosted service, while still letting an adopter self-host and modify it. This is exactly the kind of choice the owner might face if the goal shifts from "maximize contributor trust" to "prevent a bigger company from re-hosting GARBATI as a competing product." It would also disqualify GARBATI from Digital Public Good recognition, which requires an OSI-approved license.
- **MIT** (Formance) is the simplest permissive option — no patent grant, no copyleft, trivially easy for anyone to adopt and fork, but offers the least protection against a patent dispute.

**This is the owner's decision, not mine to make.** I am not recommending a license. I am naming the real, concrete tradeoff each real comparable project already made differently.

## Prioritized gap list

Each gap states: what's missing, why it matters *for this specific kind of project* (not generic OSS advice), rough effort, and whether it's an **owner decision** (something only Abubakar can resolve) or a **fill-in** (something that can be written/built directly once the owner signs off on scope/tone).

### Tier 0 — blocks basic trust or carries real legal/regulatory exposure

**G1. No LICENSE file anywhere in the platform.** Confirmed: no `LICENSE` in `garbati-platform`, and I directly checked — none exists in `LedgerApi`, `Garbati.IdentityApi`, `Garbati.OrchestratorApi`, or `Garbati.StaffIdentityApi`/`Garbati.OpsApi` repos either. Without a license, the code is "all rights reserved" by default under copyright law in most jurisdictions — nobody can legally fork, run, or build a business on it, no matter how good the README is. This is the single highest-leverage missing file in the whole platform. **Owner decision** (see benchmark table above for the real tradeoff — Apache 2.0 / MIT / GPLv2 / a source-available license each do a genuinely different job). **Effort once decided: trivial** (one file, copy the standard text, per repo).

**G2. No vulnerability-disclosure channel (`SECURITY.md`).** A core-banking codebase is an unusually high-value target — unlike most OSS, a real bug here could let someone forge an authorization grant, replay a transaction, or exfiltrate BVN/NIN. Right now, a security researcher who found a real bug (e.g., in `GrantSigner`, the ES256 signing logic Section 4 of `Garbati.IdentityApi/docs/DESIGN.md` discusses) has **no stated, safe channel** to report it privately before going public. Fineract's model is concrete and copyable: a dedicated security email, a stated private-first process, and a public report page once fixed ([fineract.apache.org/security.html](https://fineract.apache.org/security.html)). **Owner decision** on the contact channel and whether to promise a response-time SLA; **fill-in** for the document itself once that's decided. Effort: one file, but it's the one governance file where the content genuinely matters more than usual for this domain.

**G3. BVN/NIN encryption-at-rest has no concrete pattern — and the column doesn't exist yet.** Confirmed directly: `Garbati.IdentityApi/docs/DESIGN.md` Appendix B, `#TBD-4` — *"Kept to `FullName`/`Email`/`PhoneNumber` only — no BVN/NIN column... rather than guess at cryptography, that column is left out entirely pending a follow-up decision."* This blocks real Tier 3 KYC (`research/nigerian-regulatory-requirements.md`'s Q1 shows Tier 3 requires "both BVN and NIN"). It's also a live legal requirement, not just good hygiene: Nigeria's Data Protection Act 2023 requires "appropriate security measures proportionate to the sensitivity of data," explicitly including encryption at rest and in transit, as part of data controllers' security obligations (secondary-source summary, not primary NDPA text I read myself — see "what I could not verify"). I could not find a concrete, documented field-level-encryption pattern in Fineract's own public docs either — this is a genuinely under-documented area industry-wide, not a GARBATI-specific failure, but it's still the single highest-priority *domain-specific* gap because it's already explicitly flagged as "needs a follow-up decision" in GARBATI's own design doc and nothing has moved since. The standard pattern worth researching concretely in a follow-up task: **envelope/field-level encryption using a managed key-management service** (Azure Key Vault, since GARBATI already runs on Azure App Service) rather than application-level custom cryptography — this ties directly into G7 below (secrets management), since both need the same kind of managed-key infrastructure. **Owner + compliance + scholar decision** (not purely technical — retention period and even whether BVN/NIN should be stored at all versus verified-and-discarded via a third party is still open per `research/nigerian-regulatory-requirements.md`'s Q2). **Effort: a real design task**, not a single file — likely its own `T-0xx` research/design tranche before any migration is written. Per `AGENTS.md`, adding this column is both a **database migration on data model** and arguably a **new dependency** (a KMS client library) — both human-only gates.

**G4. New finding: a dated, concrete CBN data-localisation deadline nothing in the repo currently tracks.** Per multiple consistent secondary legal/industry sources ([Legal500](https://www.legal500.com/intelligence/nigeria/strategy/the-cloud-is-not-borderless-the-growing-importance-of-data-localisation-in-nigeria), [TechCabal](https://techcabal.com/2026/07/07/cbns-local-data-order-puts-nigerias-data-centres-to-test/)), **CBN Circular PSS/DIR/PUB/CIR/001/004** (issued 15 June 2026) requires that payment and financial transaction data originating in Nigeria be stored and processed **inside Nigeria** by **1 January 2027**, framed as "critical financial infrastructure" subject to domestic regulatory oversight. Coverage is described as "banks, payment service providers, fintech companies and other participants in the payments ecosystem" — **I could not confirm whether microfinance banks specifically are named**, and I could not reach the primary CBN circular text (same access problem `research/nigerian-regulatory-requirements.md` already documented with other CBN PDFs). This is directly relevant because `LedgerApi`'s README states production runs on **Azure App Service in "South Africa North"** — not Nigeria. This gap is unrelated to encryption (G3) and unrelated to anything previously flagged anywhere in `ARCHITECTURE.md` Section 9. **Correction, 22 Oct 2026 — this brief originally said the deadline was "over a year out." That was a dating error, caught on re-check: 1 January 2027 is approximately 71 days from 22 October 2026 (≈2.3 months), not over a year.** GARBATI still has no real customer data in production today, which is the real mitigating factor — but the deadline itself is close, not distant. It is a **new open question the coordinator has added to `ARCHITECTURE.md` Section 9**. **Owner decision** entirely — this is an infrastructure/hosting decision, not something a researcher resolves. See T-041 for the owner-directed follow-up research into real Nigeria-based hosting options.

### Tier 1 — blocks a real contributor or a real operator, but not urgent legal exposure

**G5. No `CONTRIBUTING.md`, and the existing docs don't actually orient an outside human.** I read `README.md`, `ARCHITECTURE.md`, and `AGENTS.md` specifically to test this honestly. `README.md` is a one-line pointer table; `ARCHITECTURE.md` is the system's source of truth but assumes fluency with the platform's own decision-numbering jargon (`P-1`, `D-2`, `#TBD-1`) from the first sentence; `AGENTS.md` is explicitly titled "Rules for every agent" and describes a workflow (`git worktree` branches, a coordinator chat session, decision numbers the coordinator assigns) built for **AI builder/QA/researcher agents**, not a human contributor who just wants to open a PR. A stranger has no single document that explains *why there are five-to-six separate repos*, in what order to read them, or what a human's equivalent of "one task = one branch = one PR" actually looks like without a coordinator chat. **This is the opposite of what I found at the per-service level** — I read `LedgerApi/README.md` and `Garbati.IdentityApi/README.md` directly, and both are genuinely strong: clear prerequisites, copy-pasteable local setup, a project-layout map, and (for LedgerApi) a live demo walkthrough. **The gap is specifically the cross-repo/platform layer, not the individual services.** GitHub's own guidance on this is a reasonable template to work from ([opensource.guide — Starting a Project](https://github.com/github/opensource.guide/blob/main/_articles/starting-a-project.md)): a CONTRIBUTING file should cover environment setup, how to propose a change, and expectations — but GARBATI's version additionally needs to explicitly translate the agent-driven workflow into a human-contributor path, which no existing comparable project's generic template covers. **Owner decision** on how much human (non-agent) contribution is actually wanted at this stage — that answer should shape the document before it's written. **Effort: a real writing task**, not copy-paste, because the translation itself is the hard part.

**G6. `CODE_OF_CONDUCT.md` and `CHANGELOG.md` are missing — pure fill-ins.** Fineract ships both; the standard, widely-adopted templates exist and need no real judgment call: Contributor Covenant for the code of conduct, and the [Keep a Changelog](https://keepachangelog.com/en/1.0.0/) format (Added/Changed/Deprecated/Removed/Fixed/Security sections, newest first) for the changelog. **Fill-in**, not an owner decision beyond "yes, add these." **Effort: trivial**, though `CHANGELOG.md` only becomes useful going forward from whenever it starts — there's no realistic way to reconstruct full historical entries retroactively with confidence.

**G7. No standard secrets-management pattern — current approach is hand-run `az` CLI.** GARBATI already does some of this well: API keys are stored as SHA-256 hashes only (never the raw key), and `LedgerApi`'s `scripts/demo-key.sh` issues/rotates/revokes per-visitor demo keys without ever printing them to a terminal. What's missing is a *documented target pattern* for where production secrets (connection strings, signing keys, API key hashes) actually live and how they're rotated, beyond "whoever has `az login` runs a command." OWASP's own guidance is concrete and directly applicable: centralize secrets in one managed store rather than scattering them across App Service settings and CI variables, prefer short-lived/dynamic credentials over long-lived static ones, and keep an audit log of who read/changed what ([OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)). Since GARBATI is already committed to Azure App Service, the natural "boring, no-new-infrastructure" answer is **Azure Key Vault with managed identity** — not necessarily HashiCorp Vault, which would be a heavier new dependency for a platform this size. This connects directly to G3 (BVN/NIN encryption needs the same kind of managed-key infrastructure). **Owner decision** — adopting any secrets-management service is both a new dependency and arguably an authentication-adjacent change, both `AGENTS.md` human-only gates. **Effort: a real design task**, likely its own research/design tranche, not a single file.

**G8. No single-command local dev experience for the whole platform.** Confirmed directly by checking all repos: `LedgerApi`, `Garbati.IdentityApi`, `Garbati.OrchestratorApi`, `Garbati.StaffIdentityApi`, and `Garbati.OpsApi` each have their own `Dockerfile`, but **none** have a `docker-compose.yml`, and there is no file anywhere that starts all five services plus their databases together. This is genuinely standard practice for a multi-service OSS project at GARBATI's scale — Fineract ships several `docker-compose-*.yml` files specifically so a newcomer doesn't have to manually wire up Postgres, migrations and the app by hand ([apache/fineract `docker-compose-development.yml`](https://github.com/apache/fineract/blob/develop/docker-compose-development.yml)). Each individual service's README already documents its own local Postgres port and `dotnet ef database update` step cleanly — the missing piece is purely the cross-service composition layer (ports that don't collide, seeded dev API keys/signing keys that match across services, one `docker-compose up` that produces a working end-to-end demo). **Fill-in/builder task**, not an owner decision beyond "yes, build this" — the per-service pieces needed (Dockerfiles, dev config patterns) already exist and are consistent across repos. **Effort: a real but bounded engineering task** (a builder-sized ticket, not a research task) — wiring five services' dev configs together, not writing new application code.

**G9. No tested backup/disaster-recovery runbook for the ledger database specifically.** `LedgerApi/README.md` already says the right thing in one sentence — *"Use a managed PostgreSQL with point-in-time recovery: the ledger's entries are the only source of truth for balances"* — which is more than many comparable projects state explicitly. What's missing is the actual **runbook**: a documented, and ideally tested, step-by-step restore procedure, a stated RPO/RTO target, and confirmation that a restore has actually been exercised at least once rather than assumed to work. This is a normal gap for a project at GARBATI's stage (Fineract's own backup guidance is similarly high-level in what I could verify, leaving specifics to the operator), but it deserves higher priority than typical OSS hygiene *specifically because* this is the one dataset in the whole platform that must never be silently lost. **Fill-in/builder task** — no new architecture decision is needed since the "managed Postgres + PITR" direction is already chosen; what's missing is exercising and documenting it. **Effort: a real task**, not a single file (a genuine restore drill against a non-production database, then write up what was learned).

### Tier 2 — real, but lower priority at GARBATI's current size

**G10. No observability beyond request logging and the audit trail.** GARBATI already has more than a bare-minimum logging story: structured per-request logs (Serilog), a correlation ID threaded across every service call, and a durable audit trail written in the same database transaction as the change it describes. What's missing is metrics (request latency/error-rate dashboards) and distributed tracing across the five services. This is **not** something I found evidence that comparable OSS core-banking projects ship as a reference setup either — Fineract's own docs leave this to the operator, same as GARBATI does today. **Recommendation: document this explicitly as a "bring your own observability" expectation** (the same posture Fineract takes) rather than treat it as an urgent build item. **Fill-in** (a documentation/expectation-setting task) now; a real Grafana/Prometheus or Azure Application Insights reference setup is a legitimate later-tranche engineering task, not urgent.

**G11. No Infrastructure-as-Code (Terraform/Bicep/Pulumi) — current deployment is hand-sequenced `az` CLI steps in GitHub Actions.** This looked, at first glance, like an obvious gap, but checking Fineract directly suggests it is **not unusually immature for a project this size**: Fineract's own README is explicit that "a proper [production] deployment can be complex, costly, and time-consuming" and does not ship a reference Terraform module for production infrastructure either — it leaves that to the operator. GARBATI's current CI-script-based approach, with each step documented in `ci.yml`, is a reasonable stage-appropriate choice for a solo developer, consistent with `ARCHITECTURE.md` P-6's existing "solo developer and budget" deployment-shape decision. **Recommendation: lower priority than it initially appears.** Worth documenting as a deliberate, named choice ("IaC is deferred, here's why") rather than silently absent, but not worth building Terraform purely for the sake of looking more mature. **Owner decision** on whether/when to invest here; not urgent.

**G12. Regulatory reporting and ISO 20022/NIBSS messaging — correctly out of scope today, but tracked incorrectly as "not needed."** Two separate findings:
- **Regulatory reporting tooling.** Fineract does ship a built-in reporting capability (a Pentaho/Jasper-based reports module per its own architecture), but even there it functions as a general reporting engine the operator configures for their own jurisdiction's requirements, not a pre-built "CBN return" template. The actual regulatory *content* (what `research/nigerian-regulatory-requirements.md` already researched) still needs to be turned into report definitions by someone — this is normal, not a GARBATI-specific gap, and correctly belongs to a later ProductApi/compliance tranche, not now.
- **ISO 20022.** `research/grpc-vs-rest-inter-service.md` already touched ISO 20022 peripherally; this research adds a concrete, current, dated fact nothing in the repo has noted: **NIBSS (Nigeria's interbank settlement operator) is actively migrating to ISO 20022** via its "National Payment Stack," unveiled June 2025 and reported in active rollout as of October 2026 ([NIBSS](https://nibss-plc.com.ng/nigerias-digital-payments-surge-to-n1-07-quadrillion-as-nibss-defines-future), [ThisDay](https://www.thisdaylive.com/2026/10/13/nibss-deploys-new-payment-stack-to-expand-instant-transfers-infrastructure/)). This means ISO 20022 is **not a hypothetical future standard GARBATI might someday need** — it is becoming the live standard any real Nigerian interbank integration will be measured against. **Correctly out of scope for now** (GARBATI has no live bank/NIBSS integration yet), but worth flagging as a fact to track, not a gap to fix today.

### Tier 3 — framing/governance items worth noting but not urgent

**G13. No stated compliance posture (PCI-DSS/SOC2/ISO 27001 — claimed, disclaimed, or silent).** I could not find Fineract explicitly claiming any of these certifications either; the ASF model is to say nothing specific and let the operator take responsibility, which is consistent with how every one of GARBATI's own prior research briefs is already written ("a qualified compliance officer must confirm"). **Recommendation: make this implicit posture explicit**, likely as a short section inside `SECURITY.md` (G2) rather than a separate document — "GARBATI makes no PCI-DSS/SOC2/ISO27001 claim; compliance is the deploying institution's responsibility" is one paragraph, not a new file. **Fill-in**, bundled with G2.

**G14. No issue templates or public roadmap — but a PR template already exists.** Worth stating plainly so this brief isn't read as "nothing exists": `garbati-platform/.github/pull_request_template.md` is real, in use, and reasonably thorough (task reference, what changed, how tested, what couldn't be verified, a LEARNING_LOG section). What's missing is GitHub issue templates (bug report / feature request) and any roadmap a stranger could read without joining the coordinator-chat process `COORDINATOR.md` describes. This connects to G5 and to a genuine, prior **owner decision that hasn't been made yet**: does GARBATI want a human-facing GitHub Issues workflow at all right now, running in parallel to the `tasks/*.md`-plus-agent process that currently drives everything? Until that's decided, issue templates would describe a workflow that doesn't actually exist yet. **Owner decision first; fill-in after.**

## What I could not verify

- **The exact scope of CBN Circular PSS/DIR/PUB/CIR/001/004** (G4) — I read only secondary legal-commentary summaries (Legal500, TechCabal); direct fetches of the primary CBN circular were not attempted beyond what these summaries describe, and I could not confirm whether microfinance banks specifically fall under it (versus only banks/PSPs/fintechs as more generically described).
- **Whether Nigeria's Data Protection Act 2023 imposes a specific, technical encryption-at-rest standard** (G3) versus a general "appropriate security measures" principle — I read only secondary NDPA summaries, not the primary Act text, and this is explicitly a different law from the CBN/AML materials `research/nigerian-regulatory-requirements.md` already researched in more depth.
- **Fineract's exact `LICENSE` file naming** — a web-fetch summary reported `LICENSE_SOURCE`/`LICENSE_RELEASE` rather than a single `LICENSE` file; I did not independently open and read both files' contents, only the summary describing them. The Apache 2.0 license *choice* itself is well established from multiple independent sources and not in doubt.
- **Cyclos's and Formance Ledger's security-disclosure and compliance posture** — search results did not surface a clear, citable answer for either; I'm reporting "not found" honestly rather than guessing.
- **Lerian Midaz's `GOVERNANCE.md` content** — a direct fetch returned HTTP 404; I only have search-result summaries describing that such a file exists, not its actual content.
- **Whether GPLv2's distribution-triggered (not use-triggered) copyleft would actually let an adopting bank run a privately modified Cyclos fork without publishing changes** — I believe this reflects how GPLv2 generally works, but this is exactly the kind of licensing-law conclusion that needs a qualified open-source-licensing legal opinion, not a researcher's reading, before anyone relies on it.
- **Apache Fineract's exact compliance claims (or disclaimers) regarding PCI-DSS/SOC2/ISO27001** — I did not find an explicit statement either way; I'm inferring "no claim made" from the absence of one in what I could search, which is weaker evidence than finding an explicit disclaimer.
- **Whether any comparable project ships a genuinely concrete, documented field-level-encryption pattern for a national-ID-equivalent field** — I did not find one in Fineract's public docs within this research's scope. This may mean it doesn't exist publicly, or may mean I didn't look in the right place (e.g., inside Fineract's Java source rather than its docs). This is a real limitation on how much "borrow their pattern" guidance I can offer for G3.
- **Fineract's CODE_OF_CONDUCT.md, CONTRIBUTING.md and SECURITY.md contents** — confirmed to exist via a web-fetch summary of the GitHub repo listing, but I did not open and read each file's full text individually; I'm reporting their existence and general purpose, not a verified word-for-word description of their contents.
