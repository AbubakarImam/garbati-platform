# IdentityApi design draft vs. established standards (T-013)

Researcher note: this checks the draft at `/Users/USER/Downloads/Garbati_IdentityApi_Design.md` (489 lines, "Status: Design draft," last updated 15 Oct 2026) against published security/standards literature on signed tokens, local verification, mandate revocation, fail-closed/audit logging, and known token-authorization failure modes. **This is pattern research, not a cryptography review, a penetration test, or a compliance/Sharia ruling.** Any Nigerian-regulatory point below must still be confirmed by a qualified compliance officer (see `research/nigerian-regulatory-requirements.md`), and nothing here is a Sharia ruling.

## Plain-language summary (read this first)

The draft asks IdentityApi to decide "is this customer allowed to do this exact transaction?" and, if yes, to issue a small, signed, 30-second ticket (a **JWT**, "JSON Web Token" — a compact, URL-safe string containing a set of signed claims) that LedgerApi checks itself, without calling IdentityApi back. A few terms used below, defined once:

- **JOSE** ("JSON Object Signing and Encryption"): the family of IETF standards that JWT belongs to — JWS (signed tokens, what this draft uses), JWE (encrypted tokens, not used here), and the key-format standard JWK.
- **`kid`** ("key ID"): a header field in a signed token that says *which* of the issuer's public keys to use to check the signature, so the issuer can rotate keys without breaking in-flight tokens.
- **Algorithm confusion / `alg` confusion**: an attack where a token checker trusts the algorithm *named inside the token itself* rather than an algorithm the checker already decided to expect — letting an attacker switch, e.g., an asymmetric signature to a symmetric one, or to `none`, and forge a token that passes.
- **Confused deputy**: a general security problem where a trusted component (the "deputy" — here, LedgerApi or the Orchestrator) is tricked into using its own authority on behalf of the wrong request, because it did not check that the thing it is honoring was actually meant for it or for this exact purpose.
- **Token substitution / mix-up attack**: a specific confused-deputy case where a token issued for one recipient or one purpose gets accepted by a different recipient or used for a different purpose than intended, because the checker did not verify who the token was for (`aud`) or what kind of token it is (`typ`).
- **Replay attack**: reusing a previously valid, still-unexpired message or token to make something happen twice.
- **TOCTOU** ("time-of-check to time-of-use"): a race condition where the state a decision was based on (e.g., "this mandate is active") can change between the moment it was checked and the moment the decision is actually acted on.
- **Fail closed / fail-safe defaults**: when a system cannot establish a positive answer, it must default to denying the action, not allowing it.

**Overall finding:** the draft's token design, local-verification pattern, revoke-and-create mandate model, and fail-closed/logging rules all match named, published practice closely — closer than many first-draft token designs reviewers see. The two places it is weaker than the strongest available guidance are (1) the example grant does not show algorithm/`kid` pinning or explicit typing being enforced on the *verifier* side, even though prose elsewhere requires it, and (2) a few specific anti-replay and key-rotation mechanics are named as "finalize before implementation" (Section 9) rather than specified now. Both are flagged as findings below, not as blockers — the draft's own open-questions list already names most of them.

## Q1: Token design (JWT/JWS) against JWT/JOSE best practice

**Short answer: the draft's claim set and stated verification rules match RFC 8725 ("JWT Best Current Practices") closely. The 30-second expiry is unusually tight compared to human-facing tokens (SAML, OAuth) but is the right order of magnitude for a machine-to-machine, transaction-bound grant, and has a close real-world analogue in PSD2's dynamic-linking codes.**

- **Algorithm pinning.** RFC 8725 is explicit: "the application MUST be configured to use a fixed, explicit allowlist of algorithms" and "MUST NOT use any other algorithms when performing cryptographic operations," because attackers have historically forced verifiers to accept `alg: none` or to flip an asymmetric signature into an HMAC check using the public key as the HMAC secret ("algorithm confusion"). The draft's Section 4.3 says the algorithm "must be configured by the application, not selected freely by token input" — this matches RFC 8725's requirement, and ARCHITECTURE.md's P-12 row names a specific algorithm (ES256). The illustrative grant in Section 3.5, however, does not show a `alg`/`kid`-pinned verifier example, so this is a documented rule, not yet a demonstrated one. [RFC 8725 §3.1](https://datatracker.ietf.org/doc/html/rfc8725); [OWASP JWT Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html) (use allowlists, not blocklists, for `alg`).
- **Key-ID-based rotation.** The draft's Section 4.3 requires "a key identifier where supported so LedgerApi can select the correct trusted public key during rotation," and names defining "current and retiring verification keys" before production — this matches standard JWKS rotation guidance, which recommends publishing (at minimum) the current and the immediately-previous key simultaneously, selected by `kid`, with the retiring key kept available until every token signed with it has naturally expired. Because grants live only 30 seconds, the required overlap window here is short compared to typical access-token rotation (which must cover hours), which works in the draft's favor. [General JWKS rotation-overlap guidance via WorkOS/industry writeups — no single RFC mandates an exact overlap duration, but the "publish both until the old key's longest-lived token expires" rule is consistent across sources checked.]
- **Audience/issuer validation.** RFC 8725 requires that if an issuer can mint tokens for more than one relying party, the token MUST carry an `aud` claim and the relying party MUST reject a token whose `aud` doesn't name it — this is exactly the token-substitution/mix-up defense described in Q5 below. The draft's claim list includes `iss` and `aud`, and Section 3.4 requires LedgerApi to check "the issuer, audience, token type/version" — this matches the RFC directly. [RFC 8725 §3.8](https://datatracker.ietf.org/doc/html/rfc8725).
- **Explicit typing (`typ`).** RFC 8725 §3.11 recommends an explicit, non-generic `typ` value specifically to prevent "cross-JWT confusion" — a token minted for one purpose being accepted where a different kind of token was expected. The draft's example grant does include `"typ": "transaction-authorization"`, and Section 3.4 lists "token type/version" as something LedgerApi must check — this matches the RFC's recommendation well, and is a specific defense worth calling out as done right (see Specific findings).
- **30-second expiry, compared to named patterns.** The draft itself frames this correctly as a "deliberately small" window tied to expected processing latency, not an arbitrary number. Compared to other short-lived, standards-governed artifacts:
  - **SAML assertions**: typical total validity is on the order of **5 minutes**, with a recommended clock-skew tolerance commonly set around **60 seconds** (and up to 300 seconds cited as an outer bound in some implementations/erratum discussion) — i.e., SAML's own "short-lived" convention is roughly 10x longer than this draft's grant lifetime, and its skew tolerance alone (60s) is twice the draft's entire grant lifetime.
  - **OAuth2 JWT access tokens (RFC 9068)**: no fixed number is mandated, but general guidance (e.g., RFC 7009's rationale for why short-lived tokens substitute for revocation) treats "minutes, not hours" as the relevant short-lived band — again longer than 30 seconds, because these tokens are meant to be used repeatedly across several API calls, not once.
  - **PSD2 dynamic linking** (EU payment-services regulation's requirement that a strong-customer-authentication code be cryptographically bound to the exact amount and payee of one transaction, and invalidated by any change to either) is the closest regulatory analogue to this draft's grant: a one-time, transaction-specific, narrowly-bound authorization artifact, not a general-purpose session credential. No source found gives PSD2's own numeric validity window, but the *shape* of the control (bind amount+payee, single use, invalidate on mismatch) is the same shape as this draft's grant — this is a real precedent for "a transaction-bound authorization artifact is a named, regulated pattern," even though it does not independently validate 30 seconds specifically.
  - **Verdict**: 30 seconds is tight compared to session-oriented tokens (SAML, OAuth access tokens) because those are built to be reused across a session; it is the right category of token for a one-shot, machine-to-machine, single-transaction grant, which is a different design problem with no single named "correct" number in the literature. The draft's own instruction to load-test before finalizing the 30-second number (Section 9, item 10 and the implementation-order list) is the correct response to this absence of a universal number, not a gap.

**What I could not verify:** no published source gives a specific recommended expiry for this exact category of artifact (signed, single-use, service-to-service, transaction-bound grant feeding a ledger) — the comparisons above are to the nearest named patterns (SAML, OAuth, PSD2), not to an exact match.

## Q2: Local verification / no synchronous call-back

**Short answer: yes, this is a recognized, named trade-off — it is structurally the same choice OAuth2/OIDC resource servers make between local JWT validation (JWKS) and online introspection (RFC 7662), and the literature is explicit that this is a straight trade between latency/availability and immediacy of revocation, not a free win.**

- RFC 9068 defines a standard JWT shape specifically so a resource server can validate an OAuth2 access token locally, "without calling an introspection endpoint" — this is the direct precedent for LedgerApi verifying IdentityApi's grant locally with a trusted public key instead of calling IdentityApi per transaction. [RFC 9068 overview, oauth.net](https://oauth.net/2/jwt-access-tokens/).
- The trade-off is described consistently across sources: local JWT validation gives "in-process signature check with no network call, surviving auth-server outages... until keys expire," at the cost that "you give up immediate revocation — a signed JWT is valid until it expires." Introspection (RFC 7662) gives "instant revocation" at the cost of "a network round trip... per request" and a dependency on the issuer's availability. One source frames the realistic middle ground as a hybrid: "local verification on the hot path, introspection or a deny list reserved for high-value tokens." [Token Introspection vs Local JWT Verification writeups](https://mojoauth.com/blog/token-introspection-vs-jwt-verification-at-scale); [RFC 7662, oauth.net](https://oauth.net/2/token-introspection/).
- RFC 7009 (OAuth2 token revocation) states this explicitly as a design principle, not a flaw: immediate revocation of a self-contained (JWT) access token "requires... backend interaction between the authorization server and the resource server" that OAuth2 does not standardize, so the recommended mitigation for the resulting exposure window is precisely to keep the token **short-lived** — "the exposure window equals... half the token lifetime [mean case], with the worst case being the whole lifetime." [RFC 7009, §3 discussion via oauth.net and secondary summaries](https://www.rfc-editor.org/info/rfc7009/).
- Applying this directly to the draft: IdentityApi's 30-second grant lifetime is the same mitigation RFC 7009 describes — accepting that a revoked mandate's already-issued grant stays valid until expiry, and bounding the resulting exposure window to 30 seconds (worst case) instead of leaving it open-ended. ARCHITECTURE.md's Section 9 (P-12) names this explicitly as the "stale window," which is the correct name for the issue per this literature.
- This exact problem — a decision made ("the mandate is active") that can be invalidated by the time it is acted on ("the grant is used") — is also the general pattern named **TOCTOU** (time-of-check to time-of-use), cataloged as [CWE-367](https://cwe.mitre.org/data/definitions/367.html): "the product checks the state of a resource before using that resource, but the resource's state can change between the check and the use in a way that invalidates the results of the check." Standard mitigation is to make the check-and-use atomic; the draft cannot make this fully atomic across two separate services and a human revocation action, so it bounds the window instead (30s) and treats reversal as a compensating recovery, not a true fix — which the literature's own framing (RFC 7009's "short-lived token as substitute for revocation") supports as the standard accepted mitigation when true atomicity is not available.

**What I could not verify:** no source was found specifically discussing this trade-off in a *banking/ledger* context (vs. the general OAuth resource-server context) — the mapping of RFC 9068/7009's reasoning onto a money-movement grant is this researcher's inference by structural analogy, not a direct banking-specific citation.

## Q3: Mandate / "power to act on an account" revocation — is revoke-and-create standard?

**Short answer: yes. "Never delete, never silently rewrite, revoke by status change and let a new grant get a new identifier" is the consistent recommendation across RBAC/NIST guidance, audit-trail standards, and real-world banking power-of-attorney practice — though the exact "revoke-and-create" terminology is this researcher's structural description, not a term found verbatim in any one source.**

- General access-control/audit guidance: "disable accounts rather than deleting them to retain audit trails," and NIST SP 800-53-aligned guidance calls for "protecting audit information against unauthorized access, modification, and deletion" while "preserving original audit content and time ordering" — i.e., a revocation event is itself a thing that must be durably recorded, not a thing that erases the prior record. One summary states the matching principle directly: "a revoke action is not evidence that access disappeared" until followed through to closure. [NIST SP 800-53-aligned summaries via nhimg.org and securends.com](https://nhimg.org/glossary/rbac-audit-logging/); [access-revocation audit-evidence guidance](https://www.securends.com/blog/access-review-audit-evidence-retention/).
- Real-world banking-adjacent precedent: for a traditional bank power-of-attorney/mandate, revocation works by notice to the institution, and the institution is "deemed to have actual notice after it has had a reasonable opportunity to act on a written notice of revocation... following receipt" — i.e., the real-world analogue also has a bounded reasonable-opportunity window between revocation and the institution actually honoring it, not instantaneous effect, and record-keeping guidance for the person revoking explicitly recommends keeping the revoked instrument on file (one legal guide recommends literally keeping a copy marked "REVOKED") rather than discarding it. [General power-of-attorney revocation guidance, legal-aid sources](https://piercelaw.com/news/estate-planning-qa-series/do-i-need-to-notify-banks-doctors-or-other-offices-that-the-old-power-of-attorney-is-revoked/). This is a useful real-world analogy for why the draft's accepted 30-second race window is not a strange invention — even paper-based mandate revocation has a non-instantaneous "reasonable opportunity to act" gap — but it is a different jurisdiction's civil/estate law, not a Nigerian banking-mandate or CBN rule, and should not be read as confirming CBN's position either way.
- The draft's specific rules — a revoked mandate's row is retained with `RevokedAt`/`RevokedBy`/`RevocationReason` (Section 2.2), "restoring access should create a new mandate with a new identifier" rather than reactivating the old one (Section 2.2), and "revoke-and-create rather than silently rewriting the old permission history" for changing authority (Section 7.3) — match this guidance point for point: never delete, never silently reactivate or rewrite, record actor+reason, give a changed grant a new identity rather than mutating the old one's meaning.
- Comparison to OAuth scopes/RBAC more generally: the same "disable, don't delete; record who/when/why" pattern is the standard recommendation for revoking any permission grant (OAuth client/consent revocation, RBAC role assignment revocation) — nothing found suggests financial-mandate revocation should, or typically does, work differently in kind from general permission-grant revocation; the differences are in *consequence* (money movement vs. generic access) and *latency requirements*, not in the revocation record-keeping pattern itself.

**What I could not verify:** no Nigeria-specific or CBN-specific rule on mandate-revocation record retention was found in this research or in `research/nigerian-regulatory-requirements.md` — that brief's confirmed retention figures (5-year AML/CFT floor, possible 6-year MFB-specific figure) are about transaction/identity records generally, not mandate-revocation records specifically; a compliance officer should confirm mandate-revocation records fall under the same retention floor.

## Q4: Fail-closed and audit/logging rules

**Short answer: yes, both sections match standard guidance closely. Fail-safe defaults is a 50-year-old named security principle and the draft's failure table implements it correctly; the logging rules match the OWASP Logging Cheat Sheet's "never log" list almost item for item. The one thing standard guidance adds that the draft does not fully spell out is an explicit statement that the log store itself is a high-value target requiring its own access control — the draft implies this but does not say it directly.**

- **Fail-safe defaults.** This is one of Saltzer and Schroeder's eight original 1975 design principles ("The Protection of Information in Computer Systems"): "base access decisions on permission rather than exclusion... the default situation is lack of access, and the protection scheme identifies conditions under which access is permitted." Modern restatements frame it as: "the default should be denial of service," and at the software level, "software that denies access when an authorization check fails to complete" is a direct, named instance of the principle. [Saltzer & Schroeder 1975, as summarized by multiple security-architecture references](https://www.jeremyjordan.me/security-design/); [general fail-safe-defaults framing](https://quality.arc42.org/approaches/fail-safe-defaults). The draft's Section 4.2 table — explicit denial stops the flow, a timeout/unavailable IdentityApi returns "a temporary-service failure, not a fabricated denial," and "an inability to establish authorization must never become permission to transact" — is a textbook implementation of this principle, and ARCHITECTURE.md's Section 1 independently states the same platform-wide rule ("Fail closed. If a service cannot establish a positive answer, the operation stops"), so the two documents are consistent with each other and with the named principle.
- **Logging — the "never log" list.** OWASP's Logging Cheat Sheet states you should never log "authentication passwords, database connection strings, encryption keys and other primary secrets, bank account or payment card holder data," government identifiers, or health/vulnerable-person data, and that "tokens, session IDs, API keys, and refresh tokens must never be logged in full." The draft's Section 6.2 list — never log raw BVN/NIN, identity documents/OCR text, API keys/private keys/access tokens/complete grant tokens, complete request bodies with personal data — maps onto this almost one-for-one. [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).
- **What standard guidance adds that the draft doesn't say explicitly.** OWASP's framing includes a reason, not just a list: "full PII payloads should not flow into the log stream because the log store itself becomes a high-value exfiltration target. The principle is to log enough to correlate the event with its actor, but not enough to be useful to an attacker who breaches the log store." The draft's Section 6.2/6.3 gives the "log enough to correlate" half correctly (CustomerId, MandateId, DecisionId, correlation ID), but doesn't explicitly say logs and audit stores need access control treated as seriously as the sensitive data they're trying to avoid holding — ARCHITECTURE.md's Section 5 shared conventions also just says "never contain identity numbers... documents, keys or full request bodies" without addressing log-store access control either. This is a minor documentation gap, not a design flaw — both documents may well intend log-store access control as a given operational requirement; it's just not written down as its own rule in either document.
- **Audit vs. diagnostic log separation.** The draft's Section 6.3 (durable, append-only, access-restricted `AuditEvents`, separate from diagnostic logs) matches the general audit-trail literature: "an append-only architecture turns the trail into an active control system" and audit records must resist "unauthorized access, modification, and deletion" — this is the same principle cited in Q3 above, applied here to the authorization-decision audit trail specifically.

**What I could not verify:** no CBN-specific rule on application/diagnostic-log content was found (confirmed already in `research/nigerian-regulatory-requirements.md` Q2 — "I could not find any CBN text that specifically addresses application/diagnostic logs as distinct from the official KYC/CDD record"). The draft's logging rule is good general practice, not something traceable to a specific Nigerian regulatory citation.

## Q5: What's missing or weak, against known failure modes

**Short answer: the draft explicitly names and defends against replay, confused-deputy-shaped mix-ups, and the revocation race (TOCTOU) — better than many first drafts. The remaining weak points are specific, narrow, and already flagged by the draft's own Section 9 as unresolved, which is the correct way to leave them, but they are real gaps against the standards checked.**

- **Replay.** OWASP/industry guidance on API replay defense calls for "a unique identifier such as a nonce or jti, server-side duplicate detection... and idempotency or one-time state for operations that must not execute twice." The draft's Section 3.7 requires LedgerApi to bind the grant to the exact request via idempotency rules and reject any grant reuse with changed fields, and Section 9 item 5 explicitly flags "define database persistence and idempotency treatment so the same grant cannot authorize a changed transaction and retries cannot create duplicate postings" as still open. ARCHITECTURE.md's Section 9 (P-12) is further along here, specifying that the ledger "stores the `decisionId` with the posting under a unique constraint, in the same transaction," which is the concrete mechanism the generic replay guidance calls for — **this is addressed, with the mechanism specified at the platform level and still pending finalization at the IdentityApi-draft level.**
- **Confused deputy / token substitution / mix-up.** The draft defends against the core version of this: the Orchestrator "cannot create or alter a valid IdentityApi grant" (Section 1.3), and LedgerApi independently re-verifies signature, `aud`, and exact transaction match rather than trusting the Orchestrator's say-so (Section 3.4) — this is precisely the "don't let an intermediate trusted party's authentication substitute for checking the actual authorization artifact" defense the confused-deputy literature calls for. One real pattern worth naming explicitly, which the draft does not call out by name: **token passthrough** — "a server accepting and forwarding an access token that was never issued for it, skipping the audience check." The draft's `aud` claim (naming LedgerApi specifically) and its instruction that LedgerApi must check audience (Section 3.4, item 3) is the correct defense against this, but the draft never states the attacker-facing scenario it's defending against (e.g., "could a grant issued for one calling service be replayed against a different consuming service, or vice versa, if Garbati ever runs more than one LedgerApi-equivalent or more than one Orchestrator?"). Given the platform's planned multi-service growth (ProductApi, OrchestratorApi, later financing services — ARCHITECTURE.md Section 2), this is worth naming explicitly in the next draft revision rather than relying on `aud` alone to be understood as the full mitigation.
- **Key compromise/rotation gaps.** The draft names key rotation as something to plan (Section 4.3) but defers "define how current and retiring verification keys are trusted before production" to Section 9 (item 6, "key lifecycle... document rotation/compromise handling"). Standard JWKS guidance is specific that the *overlap window* must be sized to the longest-lived outstanding token — here that's trivial (30 seconds), which is a genuine advantage of the short expiry, but the draft does not yet say anything about **compromise** handling specifically (i.e., what happens if a private signing key is suspected stolen — can IdentityApi revoke trust in a `kid` faster than normal rotation, and does LedgerApi have a documented emergency "stop trusting this key id" procedure?). This is a real gap against standard key-management guidance (which generally treats "planned rotation" and "emergency revocation of a compromised key" as two different procedures, not one), and it is not yet named as a separate item in either the draft's Section 9 or ARCHITECTURE.md's Section 9 — this researcher recommends it be added explicitly as a sub-item of "key lifecycle" (draft item 6 / ARCHITECTURE.md P-12) rather than assumed to be covered by ordinary rotation planning.
- **TOCTOU / revocation race.** Already covered under Q2 — the draft names and bounds this correctly; no gap beyond what Section 9 (item 7) already flags for business-side confirmation.
- **Channel-identity-to-CustomerId mapping (confused-deputy-adjacent).** The draft's Section 9 item 9 ("define how authenticated channel identities map to the internal `CustomerId` so callers cannot choose another customer's identity by editing request fields") is itself a textbook description of **BOLA** (Broken Object Level Authorization) — OWASP's #1-ranked API security risk, where "the server checks that you are logged in but not that the object you requested is yours." The draft correctly identifies this as an open risk rather than a solved one; it is appropriately flagged, not missing, but it is worth naming BOLA explicitly as the standard term for why this specific open question matters as much as it does. [OWASP API Security Top 10 — BOLA](https://blog.barracuda.com/2023/04/12/owasp-top-10-api-broken-object-level-authentication).

## What this does not settle

This research confirms the draft's token design, local-verification trade-off, mandate-revocation model, and fail-closed/logging rules each correspond to named, published practice, and flags specific places worth tightening. It does **not**:

- Decide whether to ratify the IdentityApi design draft as v2 (D-9). That is Abubakar's and the coordinator's decision.
- Resolve any of D-9's six specific items named in the task file (the decisions table itself, the token endpoint, the scope split, the Closed/Deceased cascade, freeze ownership, the one-active-mandate index) — none of those are standards questions this research can answer; they are GARBATI-specific product/implementation choices.
- Constitute a cryptography audit. No key sizes, curve choices, library vulnerabilities, or implementation-level code was reviewed (there is no code yet) — this checked only the *design's claims and stated rules* against published guidance, not an implementation.
- Constitute a compliance or Sharia review. Nothing here should be read as confirming or denying a CBN requirement or a Sharia ruling; `research/nigerian-regulatory-requirements.md`'s own uncertainty flags (exact retention period, tiered-KYC limits) stand as they were and are not resolved by this brief.
- Verify that Nigeria-specific banking-mandate revocation rules match the general RBAC/NIST/power-of-attorney pattern cited in Q3 — no CBN-specific mandate-revocation rule was found in this research or in the prior regulatory brief; a compliance officer should confirm.
- Prove the 30-second expiry is correct for GARBATI's actual infrastructure — only that it is the right *category* of number for this kind of token; the draft's own planned load test (Section 9 item 10) is the step that would actually validate it.
