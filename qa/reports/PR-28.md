## Five interview questions for the owner

1. **Q: If someone adds a 21st currency to `SupportedCurrencies` next month, what happens if they forget to add it to `FeeIncome:Accounts` but remember to update `Funding:Accounts`?**
   A: The app won't start. `FeeIncomeOptionsValidator` runs at startup (`ValidateOnStart()`) and checks every currency in `SupportedCurrencies` against the configured map; a missing one throws an `OptionsValidationException` with a message naming exactly which currency is missing, before any request can be served.

2. **Q: Today, if a chain has a Fee leg, does it have to credit the new `<CCY>200000001` Fee Income Account specifically?**
   A: No. The chain/leg validation (decision #45) only checks that a Fee or Tax leg credits *some* account where `account_class == System` — it has no idea these new accounts exist. This PR only creates and configures the accounts; nothing routes a transaction to them yet. That routing is future orchestrator work.

3. **Q: Why are there two separate option classes (`FeeIncomeOptions`, `TaxPayableOptions`) and two separate validators instead of one combined config section?**
   A: To mirror the existing `FundingOptions`/`FundingOptionsValidator` pattern exactly, and because it gives each concern its own startup-failure message — e.g. "FeeIncome:Accounts has no fee-income account for: XOF" versus a shared validator that would have to explain which of two unrelated maps broke.

4. **Q: Why is this seeded in one migration instead of two, when the funding accounts historically used two?**
   A: The funding accounts needed two migrations only because the supported-currency list itself grew over time (4 currencies, then 16 more). The currency list is already complete and fixed at 20 now, so there's no reason to seed in installments — one migration covers all 20 currencies × 2 account types (40 rows).

5. **Q: Could the new `<CCY>200000001`/`<CCY>300000001` account numbers ever collide with the existing `<CCY>100000001` funding accounts or with each other?**
   A: No — they're in deliberately different numeric ranges (100000001 funding, 200000001 fee-income, 300000001 tax-payable), and the account_number column has a uniqueness constraint. I independently checked all three seeding migrations and confirmed no account number repeats across them.
