# QA report: T-001 — LedgerApi chains of legs (decision #45)

**Scope note:** this is a post-hoc audit of code already merged to LedgerApi `main` via
PR #26 (`feature/transaction-chains`, merged as `d24a5d7`) and PR #27
(`fix/chain-error-titles`, merged as `441db93`), before this task/QA process existed. There is
no open PR to review in the normal sense. I reviewed the merged code on `main` directly,
cross-checked it against `tasks/T-001-ledger-chains.md`, `ARCHITECTURE.md` Section 12, and
LedgerApi's `docs/DESIGN.md`, and ran the test suite myself (Docker was in fact available in
this sandbox, contrary to the builder's report — see "What I verified beyond the builder's
report" below).

## Verdict: **Approve**

The implementation matches the task spec closely, follows the architecture and design docs,
handles money-safety and locking correctly, and is backed by a genuinely behavioural test
suite (not shallow/happy-path-only). I found no blockers. A few should-fix/nit items below are
about documentation hygiene and process, not the code's correctness.

## 1. Task-file conformance (point by point)

- **Data shape**: `transaction_chains` and the three new `transactions` columns match the spec
  exactly, including `NULLS NOT DISTINCT` on `(initiated_by, idempotency_key)`, unique
  `(chain_id, sequence)`, the `ck_transactions_chain_leg` and `ck_transactions_purpose` check
  constraints, and the unique `reverses_chain_id`. Verified by reading
  `src/LedgerApi/Migrations/20261015181705_AddTransactionChains.cs` directly (not just the
  entity classes) and by running `ChainMigrationTests.Migration_LeavesExistingTransactionsValid_OutsideAnyChain`,
  which inserts pre-chain rows, migrates, and asserts a half-filled leg is rejected by the
  `ck_transactions_chain_leg` constraint by name. This is a real migration test, not a
  model-diff check.
- **Leg keys / `chain:` prefix**: generated as `chain:{chainId}:{sequence}`
  (`ChainService.PostLegsAsync`), and `IdempotencyKeyRule` centrally rejects client keys
  starting with `chain:` (case-insensitive), wired into all five validators (transfer, deposit,
  withdrawal, create-account, and the chain endpoint itself — the last one is a superset of
  what was asked, see Nit #1). Tested end-to-end in `ChainApiTests.ChainPrefixedKey_Returns400_OnTheExistingEndpoints`
  for all four endpoints named in the task.
- **Endpoints and scopes**: `POST /api/chains` (`ledger.transfer`), `GET /api/chains/{reference}`
  (`ledger.read`), `POST /api/chains/{reference}/reversals` (`ledger.reverse`) — confirmed in
  `ChainsController.cs` against `LedgerScopes`. 400 for 0/>10 legs, first-leg-not-Principal, a
  second Principal, and non-positive amounts, all in `ChainRequestValidator`, all unit-tested
  including the boundary (10 allowed, 11 rejected).
- **`TransactionResponse`**: gained optional `ChainReference`, `Sequence`, `Purpose`, confirmed
  in `Contracts/Responses/TransactionResponse.cs`.
- **Posting rules**: same currency and per-currency decimal places enforced per leg
  (`LegPoster.PostLegAsync`, reused existing logic) plus a chain-wide currency-match check
  (`ChainService.PostLegsAsync`); Fee/Tax legs must credit a `System` account, checked by class
  only, not amount, exactly as specified.
- **One balance check per payer, up front**: `PostLegsAsync` derives each payer's balance once
  (`available`), before posting any leg, then accumulates what each payer has committed to pay
  (`paid`) as legs post, failing the first leg where the running total would exceed the
  up-front balance. This is functionally the single up-front check the spec asks for (the
  snapshot is taken once, before any posting) and correctly does **not** count money a payer
  receives earlier in the same chain — a dedicated test
  (`MoneyReceivedEarlierInTheChain_DoesNotCount_TowardsWhatAPayerCanAfford`) proves this.
- **Locking**: every distinct debited account is locked once, in ascending ordinal
  account-number order, before any leg posts (`PostLegsAsync`), and the reversal path locks the
  accounts the reversing legs debit in the same order (`ReverseInsideTransactionAsync`). A
  dedicated deadlock test runs 20 chains in parallel in opposite directions over the same two
  accounts and asserts all succeed
  (`OppositeDirectionChainsInParallel_OverTheSameAccounts_DoNotDeadlock`) — this is a real
  concurrency test against Postgres, not a mock.
- **Request hash**: SHA-256 of `[debit, credit, amount(G29), purpose]` per leg, narration
  excluded, matching decision #44's established pattern (`ChainService.HashLegs`). Insert-first
  on the chain row; same key+hash replays; different hash is 409
  (`ReplayAsync`/`DuplicateIdempotencyKeyException`), tested
  (`SameKey_WithAChangedFee_Returns409`, `SameKey_WithTheSameLegs_ReplaysTheChain_AndPostsOnce`).
- **Refactor, not copy**: confirmed — `LegPoster.PostLegAsync` and `LegReverser.ReverseLegAsync`
  are standalone classes taking a caller-owned `DbContext`/transaction, used by both
  `TransferService`/`ReversalService` and `ChainService`. The existing transfer/reversal
  behaviour and their tests are unchanged (275 tests pass, including the pre-existing suites).
- **Failure/retry**: business failure rolls back every leg then stores a `Failed` chain plus its
  audit row in a second save; a same-key retry returns it (tested, including the concurrent
  case: two simultaneous failing requests with one key store exactly one `Failed` chain and both
  callers see it — `TwoConcurrentFailingRequests_WithOneKey_StoreOneFailedChain_AndBothSeeIt`).
  Technical failure rolls back and stores nothing (`catch` falls through to `throw` without a
  second save); rollback uses `CancellationToken.None`, matching the spec's explicit
  instruction.
- **Audit**: one `Transfer` audit row per leg plus one `ChainPosted` row, staged before the same
  `SaveChangesAsync` that commits the postings — same DB transaction, verified by reading the
  code and by `ThreeLegs_PostSixEntries_WithCorrectBalances_AndAuditRows`, which asserts audit
  row counts directly against the database.
- **Reversal**: one reversing leg per original, last-leg-first (Tax, Fee, Principal), in one DB
  transaction, reusing `LegReverser` so each leg still gets its own `reversals` row; stored as
  its own chain with unique `reverses_chain_id`; a second reversal throws
  `ChainAlreadyReversedException` (409, chain-specific title via PR #27); any leg failing rolls
  back the whole reversal, tested with a scenario where the recipient already spent the
  principal (`ChainReversal_WhenOneLegCannotBeReversed_RollsBackTheWholeReversal`) which also
  asserts *nothing* is stored (no reversal chain row) on that path — correctly matching decision
  #27's "no failed-reversal row kept" rule. Frozen accounts may be debited by a reversal,
  tested. The old single-reversal endpoint returns 422 with a chain-specific message for a
  chain leg (`ReversalService.ReverseInsideTransactionAsync`, line ~64-70), tested
  (`ASingleLeg_ReversedThroughTheOldEndpoint_Is422_PointingAtTheChain`).
- **Tests checklist**: every single item in the task file's "Tests" section has a matching,
  behaviourally-meaningful test (see §5 below for detail on quality, not just presence).

**Nothing extra was built beyond the task's scope.** No `decision_id`/token field (#47, out of
scope) and no fee/tax system-account seeding (#46, out of scope) appear anywhere in the chain
code — confirmed by grepping for `decision_id`/`DecisionId` across `src/`, which returns
nothing. ARCHITECTURE.md §12.3 lists a `decision_id` column as part of the decision-#45 draft
data shape (left over from before #46/#47 were split out as separate decisions); the task file
itself correctly omits it, and the code correctly follows the task file, not the stale part of
the architecture draft. This is a pre-existing inconsistency in ARCHITECTURE.md itself, not a
code defect — see Should-fix #1.

## 2. Architecture / design conformance

- `docs/DESIGN.md` decision #45 (Section 9) is written up in the same style as the rest of the
  log and accurately describes what was built, including the subtlety that counting only
  pre-chain balance is conservative. Decision #26 was correctly amended by PR #27 to add the
  two chain-specific error mappings.
- No item flagged "Proposed" in ARCHITECTURE.md was built on. The chain feature is itself
  "Decided (owner)" (P-9, P-10, P-14, and decision #45 in LedgerApi's own log). The adjacent
  "Proposed" platform items (P-1 through P-6, P-13) are orchestrator/service-map concerns and
  are correctly untouched by this change — LedgerApi still "calls nobody" (decision #34/§3 of
  ARCHITECTURE.md), and the chain endpoints take no `decisionId`/token, consistent with #47
  being out of scope.
- Locking order: ARCHITECTURE.md/DESIGN.md note that decision #7's "lowest account_id" rule
  describes single-lock paths (which can't deadlock by definition) and that chains introduce
  the only multi-lock paths, using ascending **account number** (not account id) order
  consistently between the chain-posting and chain-reversal paths. I checked this reasoning
  myself rather than taking the doc's word for it: `TransferService`/`ReversalService` (via
  `LegPoster`/`LegReverser`) only ever lock one account per operation, so there is no
  cross-path lock-order mismatch to create a deadlock between a plain transfer and a chain.

## 3. Money safety

- **Rounding/currency**: decimal-places check per currency is inherited unchanged from
  `LegPoster.PostLegAsync` (existing, decision #37); chain adds a same-currency-across-legs
  check on top. G29 formatting in the request hash avoids the `100` vs `100.00` false-mismatch
  problem, consistent with decision #42/#44 precedent.
- **Balance check**: single up-front snapshot per payer, correctly excludes in-chain incoming
  credits (conservative, intentional, documented, tested).
- **Locking order**: ascending ordinal account number, deduplicated, before any posting;
  deadlock-freedom demonstrated with a real 20-way parallel Postgres test, not just asserted.
- **Idempotency**: chain-level via insert-first `(initiated_by, idempotency_key)` unique
  constraint + request hash (same mechanism as decisions #42/#44); per-leg via the
  `chain:{chainId}:{sequence}` generated key, structurally impossible for a client to collide
  with (client keys starting with `chain:` are rejected at the edge).
  Concurrent-duplicate-request race is explicitly tested
  (`TwoConcurrentFailingRequests_WithOneKey_StoreOneFailedChain_AndBothSeeIt`).
- **Reversal correctness**: last-leg-first, whole-chain-only (old endpoint 422s on a chain leg),
  second reversal refused via the unique `reverses_chain_id` constraint (race-safe: the insert
  is the check, same pattern as single-transaction reversals in decision #27).
- **Audit in the same DB transaction as the posting**: confirmed by code reading (audit rows
  are staged via `IAuditLogger.Record`, which only adds to the same `DbContext`'s change
  tracker, and committed by the same `SaveChangesAsync`/`CommitAsync` pair as the postings) and
  by a test that counts audit rows directly against the database after a real post.

No rounding, currency, balance, locking, idempotency, reversal, or audit-transaction gap found.

## Findings

1. **[Should fix]** ARCHITECTURE.md §12.3 still lists `decision_id` (unique, from the token,
   P-12) as part of decision #45's data shape. The actual build (correctly) does not implement
   this, since token verification is decision #47 and explicitly out of scope for this task.
   The platform doc should be updated to either move that column into the #47 write-up or mark
   it "deferred to #47" in #45's row, so a future reader doesn't think the shipped code is
   missing a column the architecture promised.
2. **[Should fix]** Process/tracking gap (not a code defect): `TASKS.md` still shows T-001 as
   `ready`, and the work landed via ad hoc branches (`feature/transaction-chains`,
   `fix/chain-error-titles`) before this task-board process existed. The owner should reconcile
   the board state (mark T-001 reflecting what actually happened) so the history is legible to
   future readers, per the builder's own note.
3. **[Nit]** `IdempotencyKeyRule`'s `chain:` prefix rejection is also applied to the chain
   endpoint's own top-level `idempotencyKey` (via `ChainRequestValidator` calling the same
   rule), which the task only asked for on the four existing endpoints. Harmless — a chain's own
   idempotency key lives in a different column/table than leg keys, so there's no actual
   collision risk — but it's a slightly broader rule than specified. Worth a one-line comment in
   the validator explaining this is intentional belt-and-braces, so a future reader doesn't
   "fix" it thinking it's a typo.
4. **[Nit]** The task's "bad leg lists rejected" test bullet bundles shape checks (400, caught by
   `ChainRequestValidator`) with a data check (mixed currencies, which can only be caught at
   posting time, 422, in `ChainService`). The code correctly splits these across two layers; the
   task phrasing could mislead a reviewer into expecting one single 400 test for all five cases.
   No action needed in code; flagging only so the next person reading the task file isn't
   confused.

No Blockers found.

## Interview questions for the owner

1. **Q: In `ChainService.PostLegsAsync`, why is each payer's balance derived once at the start
   of the chain instead of being rechecked fresh before every leg?**
   A: So the whole chain gets one clear "insufficient balance" answer for everything a payer
   will pay across all its legs (principal + fee + tax), instead of the principal passing and
   the fee failing separately with a confusing partial result. It's also deliberately
   conservative: money a payer *receives* earlier in the same chain is not added back into what
   it can afford to pay later in the same chain, so a chain that would technically net out can
   still be rejected — that's an accepted trade-off for a simple, predictable rule.

2. **Q: Two chains run at the same time and both touch accounts A and B, but in opposite
   directions. What stops them from deadlocking each other?**
   A: Before posting any leg, each chain locks every account it's going to debit, once each, in
   ascending account-number order (not the order the legs happen to list them in). Because both
   chains agree on the same fixed order, they'll both try to lock the same account first, so one
   just waits for the other instead of each holding one lock and waiting on the other's lock
   forever.

3. **Q: If leg 2 of a 3-leg chain fails, what actually happens to legs 1 and 3, and what gets
   stored afterward?**
   A: Nothing from any leg is kept — the whole database transaction that was posting the chain
   is rolled back, as if none of it happened. Then, in a second, separate small database save,
   the chain itself is stored with status `Failed`, which leg number failed, and why. A retry
   with the same idempotency key just returns that stored failure instead of trying again; a
   genuinely new attempt needs a new key.

4. **Q: Why does reversing a chain go last-leg-first (Tax, then Fee, then Principal) instead of
   in the original order?**
   A: It's not strictly required by double-entry math, but it matches the logical dependency:
   fee and tax exist *because of* the principal, so undoing the principal first while fee/tax
   are still outstanding would look odd operationally. It also means that if the reversal fails
   partway (say, the principal can't be reversed because the recipient already spent it), the
   fee and tax reversals that already happened get rolled back too — the whole reversal is
   all-or-nothing, same as the original post.

5. **Q: A client accidentally sends `idempotencyKey: "chain:9:1"` to `POST /api/transfers`.
   What happens, and why does the system care?**
   A: It's rejected with a 400 before anything else runs. The `chain:{chainId}:{sequence}`
   format is reserved for keys the ledger itself generates for individual legs inside a chain,
   specifically so they can never collide with a key a real client chose. If a client were
   allowed to use that prefix, there's at least a theoretical risk of ambiguity between a
   client's own retried request and a system-generated leg key — simpler to just forbid the
   prefix at the door on every endpoint that accepts a client key.
